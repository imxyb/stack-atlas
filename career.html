filecoin 大数据交易所

要点

  1. 优化链上和数据库同步问题
  • 问题：一般的同步做法是，通过订阅链上event来进行数据库同步，但是websocket链接是会偶尔断开导致同步失败。
  • 改进的办法
    1. 对于用户在前端进行合约调用的场景，后端不直接关注，而是由前端在发起合约调用完成只会，再去通过http pai的方式把这次交易的transaction hash和相关的metdata告知后端，后端拿到这些信息后再到链上进行数据获取和同步
    2. 前端http api通知的方式也是有问题的，因为发起合约调用本身是一个比较耗时的操作。有可能用户未等合约transaction结束就关闭页面或者前端由于网络抖动通知失败，那么后端就无法感知到这个transaction，就会导致和链上同步不一致了。因此这里的优化是增加全量同步。对于正在拍卖状态的数据交易进行定期全量同步，定期扫描该交易合约的链上log，并分析数据库是否尚未同步，如果是则进行同步
    3. 增加监控告警，当链上同步失败或者数据库落记录的落后最新区块过多进行人工告警介入
  1. 优化数据拍卖到期结束的延迟问题
  • 问题:
    • 当存量的auction数量增多的时候，轮询数据库成本会变高
    • 存在误点的问题，因为扫描数据库每分钟运行且串行的处理拍卖，拍卖可能不会准时结束，这样可能会导致用户超过结束时间还能进行竞价，从而产生不公平的问题，这个问题在线上也曾发生过，是个比较严重的问题
  • 改进的办法
    1. 使用redis有序集合的办法，改进前在数据库轮询拍卖到期时间，改进后则在redis进行轮询，redis内存读写效率远高于数据库
    2. 使用协程创建多个结束拍卖的worker，每个worker可以并行处理结束的流程，提升结束拍卖的效率
    3. 除了后端优化之外，还优化智能合约的竞价判断，当blocktime大于拍卖的结束时间直接抛异常不允许竞价

FEVM 浏览器

要点

  • 架构的实现

    1. filecoin生态下最有名的数据源系统是lily数据源系统，但是lily有个缺陷，需要内嵌一个完整的filecoin全节点才能运行，成本比较高，扩容也很不方便
    2. 我们自己实现的数据源系统是一个微服务架构，主要分为notify-server、task。notify-server是一个监听filecoin链上新高度的服务，调用filecoin rpc的webscoket来获取，task是一组服务，每组服务可以负责不同task的萃取，task指的是block/trasnaction/contract等数据的解析处理，task和notify-server通过redis的list消息队列作为通讯方式，notify-server把监听到的新tipset下发给task服务组，每个task服务根据自己要处理的任务进行入库解析
    3. 这个架构还有一个比filecoin官方数据源系统更优秀的地方，就是可以自动补gap，gap指的是某个高度可能丢失，导致task服务组没有成功写入这个高度的数据到数据库。task服务组会上报数据解析结果给notify server，同时notifyserver会记录每个发送的tipset以及对应的task组，一旦发现解析失败，notify server会重发这个高度的tipset到task服务组对应的消息队列，对应的task服务组会进行重试。保证了数据源系统的可靠性

  • contract verify是怎么实现的？

    1. 开发一个golang语言版本的动态获取不同版本solidity静态编译器的tool，原理就是到官方github仓库中获取不同版本的编译器web assembly代码，然后使用golang实现的的js编译器去编译这些wasm代码，再调用其中的solidity_cmplier函数来进行编译
    2. 浏览器提供一个api，获取用户指定的编译版本、编译参数、源代码等参数，再把这些参数组合成solidity指定的json-input，相当于是一个编译配置，再去调用写好的solc-go，编译出一个bytecode，再把这个编译结果和链上的合约bytecode比较，就能知道当前这个合约地址是否就是用户上传的代码，如果是，则表示合约校验成功

要点

  • 指标

    重构前：并发较高的情况下，查询券服务响应接近1s，偶发超发重发问题

    重构后：重发超发问题不再出现，查询券服务响应大概10~15ms左右

&#x9; 重构后的效果：服务职责单一，扩展性更强，耦合性更低。比如发券服务不需要那么高性能，副本数可以少一点，但对于查券和领券服务需要较高性能，可以多一些副本，原来的单体应用是做不到这样灵活的扩容性的

  • 为什么要重构

    1. 原来的发券规则都是hardcode在代码里面的，随着运营活动越多，规则越来越多，越来越复杂，在代码层面难以维护，也没办法扩容
    2. 整个券系统可以拆分为发券、领券、发券规则管理等模块，但原有系统都耦合在一起，导致系统越来越复杂，扩展性也比较差。在在一些比较热门的发券活动会偶发异常，qps无法满足一些业务场景
    3. 偶尔还会出现超发、漏发的问题

  • 如何开发规则引擎，一些细节？

    1. 把规则引擎使用trpc做成一个单独的服务，对外暴露增删改查接口，把常见的运营规则分门别类，并把规则保存到数据库中
    2. 做成了单独的服务意味着增加了一层网络调用，因此为了提升性能，这里用了redis缓存，把规则缓存起来，因为规则是大部分不需要变化的改进之后，规则从券系统中解耦，规则的维护也变得更加方便了

  • 架构的设计

    1. 梳理了整个券系统，根据业务类型拆分为发券服务、领券服务、券发佛那个规则服务，每个服务都使用trpc重写，部署在腾讯的一个k8s平台上
    2. 解决存储的问题。之前的优惠券都是单表单库存储，目前已经是过亿的级别，一些热门活动查询可能导致整个券系统变得特别慢。因此综合考虑，需要对优惠券表进行分表。这里选用了腾讯一个中间件分表，可以自定义一些路由策略或者key来让请求自动定位到特定的表。因为优惠券关联的是userid，而userid又是很重要的业务字段，经常会被用作查询条件，所以就使用了userid作为hash key来分表。同时数据库做了读写分离
      1. 用其他字段来查，需要怎么做？同步到es，如果要查其他条件，直接查es
      2. 旧数据如何做迁移的？对于增量数据，利用mysql的binlog进行同步，历史数据则使用脚本进行迁移，大概耗时半个月迁移完毕
    3. 优化热key。缓存是用redis做的，但在某些突发流量场景下可能会大量调用优惠券的查询和领券等接口，这个时候为了进一步缓解redis的压力，对于一些热key还会做一层二级缓存，具体做法是使用了腾讯内部一个hotkey检测的redis proxy，每次客户端查询一个key都会被上报到一个流计算系统里面，流计算系统会实时统计key的瞬时访问量，然后通过kafka的topic推送热key给订阅topic的客户端，从而让券系统能够感知热key并进行二级缓存
    4. 解决领券可能发生的重发和超发问题。比如一个用户重复调用了n次领券接口，可能会发生重发问题，这里使用了redis分布式锁的方式来lock住用户的请求，只有当库存扣减、写入数据库开才会unlock，超发问题的根源是库存扣减问题，为了更高的性能，选用了redis的incrby来作为扣减的实现方式，而不是直接更新数据库，redis扣减库存后同步数据库（为了更高的一致性，会有一个全量同步脚本定时校对，防止数据库和redis的不一致）。
    5. 发券服务的优化。发券和领券不一样，领券属于用户主动领券，发券属于被动领券，并且发券通常是一次性大规模并发的发送，通常一次发送量级很大，可能会达到亿级别，因此这块做了一些优化：
      1. 去除数据库事务。之前的设计是把整个发券的更新当成一个事务，要么全部成功，要么全部失败，这样效率太低了，我这里进行了一个改进，对于失败的券会记录到一个失败重试表，然后定期由程序或者人工去重发
      2. 使用消息队列。发券服务收到发券请求后，不会直接执行，而是投递到kafka的topic中，发券服务会启动n个consumer来消费消息，限制consumer数量从而限制并发的速度，从而不会造成一次性发送过大拖垮系统或者数据库的问题。
    6. 还有一个是对依赖接口做了隔离和熔断。优惠券系统内部也依赖各种第三方服务，如果第三方服务不可用会产生连锁反应造成优惠券服务也受牵连，这里使用trpc做了一个隔离和熔断机制

腾讯先享后付系统

要点

  • 如何提升海量订单代扣轮询效率

    1. 分库分表，缓解存储的读写压力。具体做法是对订单表按照userid取模的方式进行分表，分成了大概24个表。 可能会问的：
      1. 为什么要用userid而不是用视频id？因为防止数据倾斜，而且方便对某一个user进行汇总和查询，如果用视频id的话，有些视频或者剧集电影比较热门，有些很冷门，数据就可能发生倾斜了。假设需要用到其他字段来查？如果这些不算核心业务，把mysql数据表同步一份到es或者hbase之类适合存放海量数据的系统作为这些业务的存储
    2. 使用redis作为代扣订单轮询的载体，具体的实现是：
      1. 开发一个定时任务，每天凌晨12点会把第二天需要进行扣款的订单加载到redis的有序集合里面，扣款时间戳作为score，订单id作为member，一共有24个有序集合，均衡存储第二天要代扣的订单，这里分多个集合是为了避免了redis的big key问题
      2. 开发一个代扣订单服务，k8s上会部署24个这样的服务，每个服务会监听一个集合，定时按照有序集合的score-当前时间判断是否到了代扣的时间，如果到了则执行代扣逻辑
      3. 代扣逻辑执行成功，会删除redis有序集合对应的member，也就是订单id，如果执行失败则重试，重试次数超过3次则触发告警并记录，进行人工补偿

  • 如何支撑10wqps的流水推送

    1. 做好负载均衡，多个副本部署在k8s上
    2. 使用redis和lru cache做了多级缓存。因为接收服务里面有一些查询数据库和校验的逻辑，重复和大量的数据库查询会导致数据库压力过大，因此使用redis集群（3个实例）作为第二层cache，然后api服务本身也会做一个lru cache作为第三层cache。
      1. 可能会问，多级缓存如何保持一致？这里才去cache aside的方式，先更新数据库，然后删除redis缓存，再删除lru cache。（更新失败会重试，同时缓存会设置过期，因为这些数据并非很很核心的数据，即便短暂不同步也没太大关系）。还有一种实现方式，就是通过binlog来更新redis缓存和lru cache
    3. 异步处理+消息队列，提高并发处理速度。消息队列选型使用kafka，设计模型是一个topic 10个分区左右。api接收流水推送，校验成功后不会马上处理，而是会投递到kafka的topic，然后下游会启动一个消费者去消费topic，再执行流水处理逻辑
    4. 优化下游服务的调用。处理流水需要调用到其他服务的接口，我们的系统不能任意的创建无限链接或者调用下游接口，因为下游接口也有可能扛不住压力，因此我们系统也做了一些优化，比如对下游服务做了一个连接池，可以随时复用服务连接，对于一些重复参数的调用，我们也会做对调用返回的结果进行缓存来防止重复进行调用 耗时大概3~5ms

  • 如何做好重试 签约和解约回调都是非常关键的环节，一开始使用同步重试的方式，但上游服务指定时间内获取不到系统的回调响应就会重发，先享后付系统本来就已经在重试了，如果返回重复收到更多消息会出现重试风暴，因此这里做了一个优化，当先享后付系统接受到解约/签约通知的时候如果超时或者失败，都会直接给上游服务进行响应，然后对于失败的消息会扔到一个kafka mq中，由一个worker去进行定时重试，当重试失败超过阈值之后还是会使用人工补偿的方式去做

线上有一个生产者，n个消费者的系统，有一天发现消息积压告警频繁产生，但是正常来说消息处理速度应该是很快的，不应该有如此高的积压才对。然后去查看kafka的日志，会频繁发现“rebalance”字眼。重平衡是kafka为了可以用n个消费者和消费者组能够均衡消费而制定的机制，当组成员加入或者退出都会触发重平衡，消费者数量多的时候重平衡会带来一系列性能问题，然后再通过使用strace来跟踪进程系统调用，发现经常发现pid会变更，最后才想起了，消费者调用了rpc接口，这个接口偶尔会有异常，但消费者程序并没有捕捉异常，导致程序推出，而supervisor又会不断重新拉起进程，这样导致组成员频繁加入和离开，重平衡一直发生，消息的lag也越来越高，最后把程序异常进行捕获才解决这个问题

go timer泄露问题

timer泄露的问题。一开始的写法时候for + select + tick的写法：

for {
    select {
        case <- time.Tick(2 * time.Hour)
    }
}

这段代码其实有问题的，导致cpu疯狂上涨，一开始并不知道这是timer的问题，用top定位到这个应用之后，再用perf来看占用最多的cpu函数，发现最多是一个futex的函数，后面google查一下似乎是跟锁有关的。但仔细想想，代码并没有用到什么锁啊，后面在使用pprof来看，top一下，前面发现很多runtime timeproc之类的函数，然后我再google一下，发现很多人也踩过这个坑，那就是time.Tick不会被gc释放，这些timer会一直让runtime进行调度，程序运行久了之后，timer越堆越多，就导致cpu不断飙升了，最后改进办法就是使用再for循环NewTicker，这个问题也就解决了

日志通用库优化

开发了一个组内golang开发的日志公共库，主要功能就是可以统一化日志字段、格式，方便后面做日志聚合。一开始没有使用对象池，导致在某些并发过高的go程序使用的时候gc压力极大，可以用个pprof看到runtime.gc相关的函数占用比例特别高，后面发现是日志组件的问题，于是日志entry结构体进行了一个封装，放到了sync.pool中，极大的降低了gc的压力

二、Delulu 交易平台

1. 一句话介绍

一个基于 Go 微服务的多链交易平台，代码上至少拆成 market / trade / account 三个服务域，覆盖链上数据消费、行情与 K 线、交易下单、限价单/跟单、账户与钱包配置等能力。

2. 30 秒讲稿

我在 Delulu 这段经历里，能从代码坐实的部分主要是三块：第一是 theta-market 负责多链链上消费、行情和 K 线；第二是 theta-trade 负责市价单、限价单、跟单和订单调度；第三是 theta-account 负责用户、钱包、会话、收藏、快速交易配置和资产聚合。整体上不是单体服务，而是通过 gRPC、Kafka、Redis、MySQL、Asynq 这套组合把数据面、交易执行面和账户面拆开。

3. 2 分钟讲稿

如果展开讲，Delulu 不是简单的“做个下单接口”，而是比较完整的交易平台后端。

theta-market 这一侧，代码里同时有 apps/market、apps/solconsumer、apps/evmconsumer、apps/websocket。也就是说，市场服务不只是查行情 RPC，还负责消费链上数据、生成 trade 和 K 线、再通过 websocket 广播。Solana 这边代码里明确起了 70 个 block-ws 和 20 个 block-slow worker 去处理 slot 和 block；EVM 这边至少解析了 Uniswap V2 风格池子的 PairCreated / Sync / Mint / Burn / Swap / Transfer 事件。

theta-trade 这一侧，代码里能看到市价单、限价单和跟单三类核心链路。市价单会串起用户校验、钱包归属校验、行情查询、快速交易配置读取、链上交易执行、交易历史入库和 tx 状态轮询。限价单支持按价格、市值、百分比和 dev_sell 触发，创建时还会先判断当前价是否已经触发。跟单不是简单复制，而是有黑名单、市值、流动性、token age、launch rate、平台、加仓次数、金额区间等过滤条件。

theta-account 这一侧，不只是登录注册，还包括钱包登录、收藏列表、快速交易配置、资产聚合、提币前安全校验等能力。trade 会去读 account 里的 quick trade config，把 gas / maxGas / slippage / isAntiMev 这样的参数带到链上执行层。

4. 系统边界

高置信事实

  • theta-market 对外提供 market gRPC，同时包含 Sol/EVM 消费者和 websocket 广播服务。
  • theta-trade 负责订单生命周期和链上执行，不自己维护行情数据。
  • theta-account 负责用户、钱包组、会话、收藏、快速交易配置、资产聚合、提币校验。
  • 三者通过 gRPC 互调，底层至少使用了 Kafka、Redis、MySQL、Asynq。

合理推断

  • 这是按“数据面 / 交易执行面 / 账户面”拆分的交易平台后端。
  • 运行时很可能还依赖一个独立的 sign 服务，因为 trade 和 account 都有相关客户端依赖。

5. 你可以稳定讲出来的技术细节

market 侧

  • Solana 消费侧会启动 70 个 block-ws 和 20 个 block-slow BlockService。
  • ProcessBlock 会计算 solPrice、解析交易、保存 trades/accounts/token accounts，并触发后续 MQ 逻辑。
  • EVM 消费侧至少覆盖 Uniswap V2 风格池子的创建、同步、铸造、销毁、交易、转账事件解析。
  • TradeConsumer 会先做交易去重，再更新 pair cache、trade cache、热度数据，并在 prod 下生成 K 线。
  • K 线聚合字段不只包括 OHLC，还包括 FDV、高低点、均价、买卖次数、买卖成交额。
  • SOL/BSC 额外支持 1s K 线，其它链从 1m 开始。
  • GetKline 查询前会先用 singleflight 合并并发请求。
  • K 线查询代码优先走 KlineDDB。
  • websocket 侧有专门的广播逻辑，不只是被动转发原始数据，例如 market 会把 token K 线通过 websocket 服务广播出去。

trade 侧

  • 市价单链路会串联：用户鉴权 -> 钱包归属校验 -> pair info 查询 -> 交易配置查询 -> ChainManager.Trade -> 历史入库 -> tx 轮询。
  • 限价单支持 price / market_cap / percentage / dev_sell 四类触发条件。
  • 限价单创建时会先做链上余额校验。
  • 如果限价单创建时已经达到触发条件，会直接创建 LimitOrderFillTask。
  • 限价单执行侧使用 DB 状态切换防重入，并用 Redis 记录错误次数做指数退避。
  • 跟单链路明确要求 follow_address 是 Solana 地址。
  • 跟单过滤条件至少包括：黑名单、市值、流动性、token age、launch rate、买入金额、平台、加仓次数。
  • 调度层同时用了 gocron + asynq + Redis。
  • trade 服务通过 DataClient 统一依赖 market / account / sign / websocket，不是把外部 RPC 散落在各处。
  • 下单请求里传入的钱包地址不会被直接信任，而是会重新根据 OmniAccount + WalletGroupId + ChainType 反查地址并校验。
  • GetTradeConfig 实际读取的是账户侧的 QuickTradeConfig，说明执行参数和账户配置是连通的。

account 侧

  • 钱包登录是标准消息签名校验，代码里有签名时间窗判断。
  • 快速交易配置默认会生成 P1/P2/P3 买卖共 6 条配置。
  • 配置字段至少包括 gas_type / is_anti_mev / slippage / gas / max_gas / swap_type。
  • 收藏列表优先读 Redis，miss 后回表并批量调 market.GetMultiMarketInfo 补齐。
  • 资产查询是并发拉各钱包资产并更新总价值。
  • 提币前会做 24 小时内改密限制、邮箱/TOTP 校验、自转检查。
  • 钱包登录消息带有 timestamp，服务端会校验与当前时间的偏差，超出 45min 直接拒绝。
  • 验签不是自定义格式，而是标准 \x19Ethereum Signed Message 前缀消息恢复地址。

5.2 两条端到端链路

链路一：Delulu 市价单

  1. 进入 CreateMarketOrder 后先从 header 里取授权用户信息。
  2. 通过 OmniAccount + WalletGroupId + ChainType 去外部能力反查真实钱包地址。
  3. 把反查结果和请求里的 WalletAddress 比对，不一致直接拒绝。
  4. 校验订单类型只能是 FAST 或 MARKET。
  5. 通过 market.GetPairInfo 获取 pair、token、base token、价格、精度、swapName 等信息。
  6. 通过 account.QuickTradeConfig 读取 gas / maxGas / slippage / isAntiMev / gasType。
  7. 根据买卖方向把输入数量换算成链上最小单位；如果是 sell all，还会额外查链上余额。
  8. 如果请求带 ExpectAmountOut，会结合滑点算出 amountOutMin。
  9. 把所有执行参数交给 ChainManager.Trade 真正发起链上交易。
  10. 下链返回后再异步写 trade_history、记录时延统计，并继续做 tx 状态轮询。

链路二：Delulu 跟单

  1. FollowOrderConsumer 监听市场 trade 消息。
  2. 先根据 maker 找出当前所有 running follow orders。
  3. 命中后先写一条 follow_history，不是先执行再补历史。
  4. 做一轮条件过滤：黑名单、市值、流动性、token age、launch rate、平台、金额区间、加仓次数等。
  5. 如果是买单，会基于策略和 native token 价格计算跟买金额。
  6. 更新 follow_history 的 base amount / follow amount。
  7. 优先放入全局跟单队列调度器；如果没有，就退回到 asynq task。
  8. 如果是卖单，则按 sell type 分流到自动跟卖或其他策略。

5.3 限价单如何讲“更快、更准”

这是 Delulu 里一个很适合面试展开的点，因为代码上能明确看出它不是“定时全表扫一次看看有没有触发”，而是更偏实时事件驱动。

一句话包装

限价单这块更适合讲成：用市场成交流实时触发，用订单类型语义精确判定，用异步执行和状态机防止重复触发。

如果面试官问“你们是怎么做到更快触发的”

可以这么答：

不是靠低频 cron 扫全表，而是直接消费 market 侧解析出来的 trade 流。trade 服务收到一批成交后，会先提取这批成交里每个 pair 的最新价格，再只查询这些受影响 pair/token 对应的 waiting 订单，命中后立即 enqueue 限价单执行任务。再加上创建订单时会先做一次“当前价格是否已经触发”的即时判断，所以触发路径既有创建时快路径，也有交易流实时路径。

如果面试官问“你们是怎么做到更准确触发的”

可以这么答：

准确性主要来自三层。第一层是触发判定规则比较明确，买入限价、卖出限价、止损、止盈各自有不同的价格比较逻辑，不是所有订单都共用一套规则。第二层是触发不是靠过时缓存，而是用 market 侧刚解析出的最新成交价。第三层是触发后不会直接改成成功，而是进入异步执行和链上 pending 状态，再通过 tx 状态轮询做最终确认，所以“触发”和“最终成交”是分开的。

代码能坐实的“快”

  • 限价单触发入口在 TradeConsumer.handleLimitOrder，直接消费市场 trade 批次，而不是周期性全表扫描。
  • 一批 trades 进来后，会先提取这批里涉及的 pairs 和 tokenCas，然后只查这些范围内、当前 waiting 状态的 triggerable orders。
  • 普通限价/止盈/止损按 pair_ca 查；跟单止盈止损按 token_ca 查，缩小了扫描范围。
  • 创建限价单时就会拿一次当前 pairInfo.TokenPrice 调 IsTriggeredLimit，如果已经满足条件，会立即创建 LimitOrderFillTask，不等下一笔市场消息。
  • 触发后不是同步阻塞执行，而是直接 enqueue TypeLimitOrderFill 异步任务，减少用户请求线程的等待。

代码能坐实的“准”

  • 触发规则不是模糊判断，而是在 IsTriggeredLimit 里按订单类型分开：
    • 买入限价：priceUsd < limitPrice
    • 卖出限价：priceUsd > limitPrice
    • 止损：priceUsd < limitPrice
    • 止盈：priceUsd > limitPrice
  • TradeConsumer 对同一批 trades，会取每个 pair 的最新 trade 价格作为这次触发判断依据。
  • 真正执行任务前，LimitOrderProcessor.FillLimitOrder 会再次拉最新 pairInfo，重新取 TokenPrice / BaseTokenPrice / NativeTokenPrice / Decimals 来计算 amountIn 和 amountOutMin，不是完全沿用下单时的旧快照。
  • 创建订单时已经先做余额校验；执行时还会读取最新 quick trade config，把当前 gas / maxGas / slippage / isAntiMev 带入交易。
  • dev sell 是单独一条触发路径，不跟普通价格型限价单混在一起。

代码能坐实的“不会乱触发、不会重复触发”

  • 执行前先通过 SetHandling 抢 DB 状态锁，没拿到锁的任务会直接退出，避免同一订单并发重复成交。
  • 如果执行失败，会把状态退回 waiting，而不是卡死在中间态。
  • 失败重试不是无脑重试，而是 Redis 记录 order_error:<id>，按指数退避控制重试间隔。
  • 成交上链后会先进入 CHAIN_PENDING，再由 HandlePendingOrders 轮询 tx 状态，把订单标记成 success 或重新退回 waiting。
  • 如果 waiting 太久没触发，会被 ExpireOrdersByTime 标成 expired，避免老订单长期占系统资源。

适合面试时直接说的版本

“限价单这块我们不是靠低频扫表触发，而是用市场成交流做实时触发。trade 服务收到一批成交后，会先提取受影响的 pair 和 token，只查这些范围内的 waiting 订单，然后按订单类型做精确判断，比如买入限价是最新成交价低于限价才触发，卖出限价和止盈止损又是另一套比较规则。命中后不会在请求线程里直接执行，而是进入异步任务；真正执行前还会再拉一次最新 pair 信息，重新计算 amountOutMin。为了避免重复触发，执行前会先抢订单 handling 锁，失败会退回 waiting，并通过 Redis 做指数退避。所以上层看起来是‘触发快’，底层其实是‘事件驱动 + 精确规则 + 状态机防重’。”

不要乱说的边界

  • 不要说“毫秒级触发”或“比竞品快多少”，当前代码能坐实的是触发方式和架构，不是延迟指标。
  • 不要说“完全不会漏触发”，更稳妥的说法是：它采用事件驱动触发和状态机补偿，目标是尽量快、尽量准，并对失败场景有回退机制。
  • 不要说“执行前一定会再次校验是否仍满足限价条件”。当前代码能确认的是执行前会重新拉 pair info 计算交易参数，但不是再次调用 IsTriggeredLimit 做二次价格判断。

7. 高频追问与答题要点

问：三个仓库怎么拆职责？

答：theta-market 管链上消费和行情，theta-trade 管订单和链上执行，theta-account 管用户、钱包和配置。trade 会依赖 market/account/sign/websocket，account 也会依赖 market/trade/sign。

问：K 线怎么来的？

答：不是直接查外部行情接口，而是 market 消费 trade 流后实时聚合。TradeConsumer 收到 trade 后会去重，再按 pair + interval 更新 OHLC、均价、买卖量，最后写缓存/库并推 websocket。

问：为什么你说这是“实时链路”而不只是离线索引？

答：因为代码里是 slot/block 异步消费，处理完交易后直接进入 trade MQ，再向下游做 K 线拟合和推送，这明显是偏实时增量处理的架构。

问：限价单怎么避免重复执行？

答：执行时先切 DB 状态，再结合 Redis 错误计数做退避；失败后把状态切回等待，不是无保护地反复提交链上交易。

问：跟单为什么不是简单复制？

答：代码里明确有一套过滤条件，不只是跟地址。会看黑名单、市值、流动性、token age、平台、金额区间、加仓次数等条件，说明它是有策略约束的。

问：账户服务除了登录还有什么？

答：还有 quick trade config、收藏列表、资产聚合、提币校验等。交易服务会实际读取 quick trade config，把交易参数带到执行层。

问：你在这个项目里能举一个“不是 CRUD”的模块吗？

答：K 线聚合、限价单调度、跟单过滤都可以。它们都有明确的状态流转、调度和策略逻辑。

问：为什么下单前还要反查钱包地址？

答：因为请求参数里的地址不能直接信。代码里会根据 OmniAccount + WalletGroupId + ChainType 去反查真实地址，再和请求地址比对，这一步本质上是在做账户归属校验。

问：你们的限价单为什么能更快触发？

答：因为它不是定时扫全表，而是直接消费市场 trade 流。每批成交进来后只提取受影响的 pair/token，再查询这些范围内的 waiting 订单；另外创建订单时还会做一次即时触发判断，所以既有创建时快路径，也有实时交易流触发路径。

问：你们的限价单为什么说更准确？

答：更准确主要来自三点：一是按订单类型分开比较规则，不是所有订单共用一套条件；二是触发价格来自 market 刚解析出来的最新成交价；三是触发后还会走异步执行、pending 状态和 tx 轮询，最终成交确认和“触发命中”是分开的。

问：怎么避免同一个限价单被重复触发多次？

答：执行前会先用 SetHandling 抢订单状态锁；没抢到锁就不执行。执行失败会退回 waiting，且 Redis 会记录错误次数做指数退避，所以不是简单地并发重复打一笔单。

问：quick trade config 具体影响了什么？

答：它直接影响执行层参数，至少包括 gas / maxGas / slippage / gasType / isAntiMev。也就是说，这不是前端展示配置，而是下单前真实会读取的参数。

问：钱包登录怎么防重放？

答：签名消息里有 timestamp，服务端会校验时间偏差，超过 45min 直接拒绝；同时验签用的是标准 Ethereum Signed Message 格式。

问：为什么收藏列表不直接每次都查 market？

答：代码里明显是 Redis 优先、数据库补偿、再批量调 market，这说明这条链路很在意聚合成本和接口效率。

问：跟单任务为什么有“队列调度器”和 asynq 两种路径？

答：更稳妥的说法是当前实现同时兼容了集中排队和异步任务两种执行方式，优先走全局队列调度器，没有时再退回 task。

三、RFQ 现货交易平台

1. 一句话介绍

这是一个链上 RFQ 现货交易体系，代码上至少分成三层：链上合约执行层 rfq_contracts_v2，链下报价与签名编排层 swap-engine，以及成交行情与 K 线服务 rfq-market。

2. 30 秒讲稿

RFQ 这块我建议讲成三层架构。链上是 Router -> Settlement -> Vault，分别负责资金入口与多腿聚合、平台签名/fee/nonce/partial fill 校验、maker 侧执行。链下是 swap-engine，它维护本地订单簿、接收 MM 的深度、模拟拆单、并发请求 MM 的 firm quote、再返回可直接上链的 calldata。成交后还有 rfq-market 消费 trade 事件，做 K 线和 overview 服务。

3. 2 分钟讲稿

如果展开讲，RFQ 这套系统的关键不是“有个合约能 swap”这么简单，而是链下报价和链上强约束怎么配合。

链上这层，Router 负责统一入金、Permit2、原生 ETH 包装成 WETH、多腿聚合执行以及残余资产退款；Settlement 负责验证平台签名、收手续费、消费 maker nonce、限制 partial fill 偏离、并通过 callback 把净输入打给 Vault；Vault 则代表 maker 执行侧，代码里至少有库存模式的 MMVaultExample、基于 Uniswap/Pancake V3 的 V3BasedVault、以及兼容 Ondo 的 OndoVault。

链下这层，swap-engine 不是直接问单个 MM 要报价，而是先根据本地 orderbook 做 SimulateSwap，把大单拆成多条腿，再并发向命中的 MM 请求 firm quote。拿到结果后，它会聚合 amountOut，生成外层签名和 Router 调用所需 calldata。

数据侧，rfq-market 不参与撮合和结算，它消费 trade Kafka 事件，归一化 base/quote 方向，写 trade 表、聚合多周期 OHLCV，再通过 gRPC/WebSocket 给前端提供 K 线和 overview。代码里还能看到它在没有 K 线时会调用 swap-engine 的 indicative quote 做价格兜底。

4. 系统边界

高置信事实

  • rfq_contracts_v2 是链上执行层，核心调用链就是 Router -> Settlement -> Vault。
  • swap-engine 是链下报价与签名编排层。
  • rfq-market 是成交数据、K 线、概览与 websocket 服务。
  • rfq-market 会调用 swap-engine 的 indicative quote 作为现价兜底。
  • swap-engine 和 MM 之间通过 WebSocket 二进制 proto 交互。

合理推断

  • 这三个仓库属于同一 RFQ 现货业务线，但不一定完全是同一代代码。
  • 本地 swap-engine 的 calldata 编码接口和 rfq_contracts_v2 的新 Router 接口有代际差异，更适合讲成“同一业务线的不同阶段实现”，不要直接说它们百分百一一对应。

5.2 两条端到端链路

链路一：firm quote -> 链上结算

  1. 用户请求 swap-engine.GetFirmQuote。
  2. quote_service 先解析 amountIn，按 apiKey 扣费。
  3. quote_aggregator 找 matcher，调用 SimulateSwap 在本地订单簿拆单。
  4. 拆单结果被转成多条 QuoteLeg。
  5. mm_ws_client 并发向各个命中的 MM 发送 QuoteRequest。
  6. 各腿返回 QuoteResponse/SignedOrder 后，客户端校验签名长度、extraData、amountIn、amountOut、nonce。
  7. 全部成功后聚合成一笔 TradeStructure，生成 quoteID / nonce / totalExpectedOut / totalMinOut。
  8. txbuilder 生成外层签名和 Router 调用所需 calldata。
  9. 用户把 calldata 提交到链上 Router.swap。
  10. Router 负责拉资金、处理 Permit2 或 WETH、逐腿调用 Settlement.settle。
  11. Settlement 验平台签名、扣 fee、消耗 nonce、准备 callback validation。
  12. Vault 验 maker 签名并执行实际 swap/mint/redeem。
  13. Settlement 用 recipient balance delta 检查 amountOut。
  14. Router 汇总结果并把残余资产退回用户。

链路二：trade event -> K 线 / overview

  1. 成交结果进入 rfq-market 的 Kafka consumer。
  2. consumer 先把消息反序列化成 trade event。
  3. trade 会先尝试落库，再进入聚合器。
  4. Agg.HandleTrade 归一化 base/quote 方向并更新多周期 snapshot。
  5. flushLoop 周期性 drain 脏数据。
  6. flushOnce 按 interval 批量 upsert K 线。
  7. flush 后把最新 candle 广播给 websocket。
  8. GetPairOverview 查询时，当前价优先从 SwapService.GetIndicativeQuote 获取。
  9. 再结合 quote USD 价格、24h 统计、supply 元数据，计算 priceUsd / change / volume / fdv / marketCap。

5.3 关键机制拆解：做什么、原理是什么、解决什么问题

1. RFQ 为什么采用“链下报价、链上结算”

RFQ 和纯 AMM 的思路不同。AMM 的价格主要由链上池子曲线决定，而 RFQ 是先由做市商针对用户的交易规模给出报价，再把报价签名带到链上完成结算。

这样设计主要解决三个问题：

  • 报价计算、订单簿模拟和多做市商拆单放在链下完成，避免把复杂撮合逻辑和大量中间状态放到链上。
  • 做市商可以结合自己的库存、风险敞口和外部流动性给出 firm quote，而不是只能被动接受一条固定 AMM 曲线。
  • 最终资金转移仍在链上原子执行，并通过签名、Nonce、deadline 和 amountOutMin 把链下承诺变成可验证的链上约束。

因此这套系统的核心不是“信任链下服务算出的结果”，而是“链下负责高效地产生报价，链上只接受满足签名和风控条件的报价”。

2. Permit2 具体用来做什么

普通 ERC20 交易通常需要用户先给业务 Router 发一笔 approve，再发一笔 swap。如果换一个 Router，往往还要重新授权。Permit2 把 Token 授权集中到一个通用合约：用户先把 Token 授权给 Permit2，后续每笔交易可以通过链下签名给出一次性、带金额和过期时间的拉款许可。

在这套 RFQ Router 中，资金入口分为：

  • 普通 ERC20 transferFrom：用户直接调用，且已经授权 Router。
  • Permit2 allowance：使用用户预先配置在 Permit2 中的 allowance。
  • Permit2 signature：用户对本次 Token、金额、Nonce 和 deadline 进行链下签名，由 Permit2 验签后把资金转给 Router。
  • Permit2 witness signature：在基础 Permit2 授权之外，再把本次 RFQ swap 的业务参数一起签进去。
  • 原生 ETH：Router 收到 ETH 后包装成 WETH，统一进入 ERC20 结算链路，剩余部分再解包退款。

需要讲清楚一个边界：Permit2 不是“永远不需要 approve”。用户首次使用某个 Token 时，通常仍需把 Token 授权给 Permit2；它解决的是后续不必针对每个业务 Router、每笔交易重复授权，并允许用链下签名表达单笔许可。

3. Permit2 witness 的原理，以及为什么 relayer 场景必须用

只有普通 Permit2 签名时，授权重点是“这个 Token 最多可以拉多少、Nonce 是什么、什么时候过期”。但 relayer 代发时，msg.sender 不是用户。如果签名没有绑定业务参数，中继方理论上可能替换实际调用里的收款人或滑点参数。

本项目把下面这些字段编码成 EIP-712 witness：

from / to / inputToken / outputToken / amountIn / amountOutMin / deadline

执行过程是：

  1. 用户根据本次 swap 的完整参数计算 witness，并签署 Permit2 typed data。
  2. relayer 携带 swap 参数、witness 和签名调用 Router。
  3. Router 不直接相信传入的 witness，而是用实际调用参数重新计算。
  4. 两者不一致时，Router 以 Permit2WitnessMismatch 回滚。
  5. 一致时，再调用 Permit2 的 permitWitnessTransferFrom；Permit2 验证签名、Token 权限、金额、Nonce、deadline 和 witness 后才转账。

因此 witness 的本质是把“资金授权”与“这笔具体交易的业务意图”绑定起来。它防的不是做市商报价伪造，而是代发方拿着用户的资金许可，篡改接收地址、交易币种、输入金额或最低输出。代码中 from != msg.sender 的 relayer 路径强制要求 witness，普通 ERC20 allowance 和无 witness 的签名都不能代替它。

另一个边界是：当前 witness 绑定的是用户授权的 7 个交易参数，不包含完整 RFQ 报价数组。完整报价内容由后面的平台签名和 maker 签名保护。代码虽然提供了 hashRFQQuotes，但当前 Router 的 witness 路径没有使用它。

4. 为什么需要平台签名和 maker 签名两层授权

两层签名控制的是不同权限：

  • maker 签 MMQuote：证明做市商愿意按指定的 vault / executor / token / amount / deadline / nonce / extraData 执行这份报价。
  • 平台签 RFQQuote：对 MMQuote 结构化字段的哈希以及 feeTo / feeRate 再签一次，证明平台已经接受这笔报价和收费规则；该哈希不包含 mmSignature 字节，maker 签名由 Vault 独立验证。

Settlement 验证平台签名，具体 Vault 验证 maker 签名。这样既不能由平台单方面伪造 maker 的资金承诺，也不能由 maker 绕过平台规则随意改变手续费或结算入口。

签名采用 EIP-712 结构化数据，字段类型明确，且 domain separator 会绑定 chainId 和 verifying contract。它比直接签一段不透明字节更容易让前端展示签名内容，也能降低签名被复制到另一条链或另一个合约使用的风险。

5. bitmap Nonce 怎么防重放，为什么不用单调递增 Nonce

做市商报价可能并发产生，也可能不按签发顺序成交。如果只维护一个单调递增 Nonce，先成交较新的报价可能导致更早但仍有效的报价无法使用。

Settlement 把每个 maker 的 Nonce 分成：

wordPos = nonce >> 8
bit     = 1 << (nonce & 0xff)

每个 uint256 bitmap 可以记录 256 个 Nonce。结算时检查对应 bit 是否已经置位；未使用则置 1，已置位则以 NonceAlreadyUsed 回滚。这样既支持报价乱序成交，又比为每个 Nonce 单独存一个 bool 更紧凑。Permit2 自身还会消费资金授权签名里的 Nonce，两层 Nonce 分别防止“拉款授权重放”和“maker 报价重放”。

6. Settlement callback 为什么要用 transient 上下文

Settlement 不会在一开始就无条件把用户资金打给任意 Vault。它先完成：

  1. 平台签名、deadline、executor、fee 和 partial fill 检查。
  2. 扣除平台手续费，得到净输入金额。
  3. 消费 maker Nonce。
  4. 把本次允许拉款的 vault / payer / inputToken / amount 写入 transient 状态。
  5. 调用指定 Vault 的 swap。

Vault 需要输入资金时反向调用 rfqSettleCallback。Settlement 会检查 callback 发起者就是当前指定 Vault，然后先清空 transient 状态，再执行精确金额的 transferFrom。提前清空使同一执行上下文里的第二次 callback 无法复用授权；如果后续 swap 失败，整笔交易回滚，手续费、Nonce 和转账也会一起恢复。

这里使用 transient storage 的原因是这些字段只在当前交易执行期间有效，不需要永久写入链上状态。它同时把付款权限收敛为“一次结算、一个 Vault、一个 Token、一笔净输入”，减少恶意 Vault 或错误 callback 多拉资金的空间。

7. 为什么结算要看余额差，而不是相信 Vault 的返回值

Vault 是可插拔的外部执行层，Settlement 不能只相信它返回的 amountOut。代码会在调用 Vault 前后分别读取接收方的输出 Token 余额：

actualAmountOut = balanceAfter - balanceBefore

只有实际余额增量达到按报价、time decay 和 fill 比例算出的 amountOutMin，结算才成功。Router 在多腿全部完成后还会对聚合后的 totalAmountOut 再检查一次用户级 amountOutMin。

这形成两层输出保护：Settlement 保证每条 RFQ 腿实际到账不低于该腿要求，Router 保证多腿聚合后的总输出不低于用户接受的最低值。它避免恶意或异常 Vault 只返回一个好看的数字却没有真正把资产转给用户。

8. partial fill 和 time decay 如何配合

Settlement 允许实际 amountIn 小于做市商完整报价的 mm.amountIn，但向下偏差不能超过 6000 bps，也就是实际输入至少为原报价的 40%。这既支持一定程度的部分成交，又避免把针对大额询价的价格无限缩小后用于小额交易。

这里的 partial fill 是“这次可以只成交报价量的 40%～100%”，不是同一报价可以反复分批成交。无论实际执行比例是多少，Settlement 都会消费整个 maker Nonce，第二次提交同一报价会按重放回滚。

最低输出不是简单按固定价格计算，而是分两步：

  1. 用 T / N / M / E 模型对完整报价的 amountOut 做时间衰减：
    • N：开始衰减的时间。
    • T：衰减持续时间。
    • M：最大下降幅度，Settlement 额外限制不超过 500 bps。
    • E：衰减曲线指数，决定线性或非线性下降速度。
  2. 再按照扣费后的实际输入占完整报价输入的比例，计算本次 amountOutMin。

公式可以简化为：

decayedOut = amountOut - amountOut * M / 10000 * (elapsed / T) ^ E
amountOutMin = decayedOut * actualAmountIn / quotedAmountIn

其中 elapsed 会被截断在 [0, T]。这套机制表达的是“报价越接近过期，做市商允许的最小输出可以按预设曲线下降”，同时仍受最大降幅、deadline 和最终余额差校验约束。

9. 不同 Vault 的执行边界有什么区别

  • MMVaultExample：库存模式参考实现。校验 maker 签名并收到输入后，直接从 Vault 库存向用户支付输出资产。
  • V3BasedVault：把输入继续路由到 Uniswap V3 或 Pancake V3 pool。它用 transient activePool / activeInputToken / activeInputBudget 约束 V3 callback，只允许当前池子在预算内扣款。
  • OndoVault：把 extraData 解码为 Ondo Quote + attestationSignature，按 BUY / SELL 进入 mint 或 redeem；使用 UUPS 保持升级能力，并兼容旧接口和 RFQ v2 Settlement 路径。

三种 Vault 说明 Settlement 只负责统一的报价与资金安全规则，具体流动性来源可以替换。新增执行场景时不需要把库存、V3 pool 或 RWA mint/redeem 逻辑继续堆进 Settlement。

7. 高频追问与答题要点

问：为什么要拆 Router、Settlement、Vault？

答：因为三层职责完全不同。Router 是用户资金入口和多腿聚合，Settlement 是平台规则和安全校验，Vault 是 maker 执行侧。这样资金路径、平台约束和做市执行边界是分开的。

问：为什么要两层签名？

答：平台签名负责“这笔 RFQ 允许进入结算”，maker 签名负责“这份报价确实来自做市商”。两层签名把平台风控和 maker 授权解耦。

问：Relayer 代发怎么防止篡改接收人和滑点？

答：Router 的 Permit2 witness 里会绑定 to 和 amountOutMin，还有 token、amountIn、deadline。witness 不匹配会直接回滚。

问：partial fill 怎么控制风险？

答：代码里明确限制实际成交输入不能大于报价输入，向下偏离最多 6000 bps，同时输出按比例并叠加 time decay 计算。

问：为什么 Settlement 用 callback 给 Vault 打款，而不是 Vault 直接拉？

答：这样平台层可以先完成 fee、nonce、签名和 amount 约束，再把“已验证的净输入”通过 callback 交给 Vault，边界更清晰。

问：V3 callback 怎么避免池子多扣款？

答：V3BasedVault 维护 activeInputBudget，callback 时会消费预算，超额会直接回滚。

问：为什么 swap-engine 要先本地模拟再去找 MM 要 firm quote？

答：先用订单簿做拆单和份额分配，可以避免盲目向所有 MM 广播。只有命中的腿才去请求真实 quote 和签名。

问：如果某个 MM firm quote 失败怎么办？

答：当前代码更偏“要么整笔成功，要么报错”，没有看到部分成交或失败腿重撮合逻辑。

问：Settlement 的 callback validation 在防什么？

答：它在防 Vault 在错误上下文下拉走用户资金。Settlement 会把 amount / inputToken / vault / payer 这些 transient 状态准备好，只允许当前 Vault 在这次结算里通过 callback 拉走净输入。

问：为什么 nonce 用 bitmap？

答：更稳妥的说法是：代码采用 wordPos + bit 的 bitmap 结构来管理 maker nonce 消耗状态，比单 nonce 独立映射更紧凑，且容易做已消费检查。

问：time decay 怎么讲得具体一点？

答：不要只说“支持衰减报价”。应该说 RFQLib 用 T / N / M / E 四参数模型算 decayedAmountOut，而 Settlement 在算 amountOutMin 时会先衰减，再按实际 fill 比例换算。

问：MM WebSocket 接入有什么保护？

答：代码上至少能坐实两层：一层是 token/JWT 认证；另一层是 DepthSnapshot 进来时会做 pair 白名单校验，不在白名单就拒绝更新本地 orderbook。

问：rfq-market 为什么要 leader election？

答：因为 market 可能多实例部署，但 K 线拟合不希望多实例重复消费同一条 trade，所以 RedisLock 保证同一时刻只有一个实例成为 leader。

问：overview 的 price source 为什么值得讲？

答：因为很多人会默认 overview 当前价就是最近一根 K 线 close，但这里代码明确写了当前价优先来自 swap-engine 的 indicative quote，这是个很具体的实现细节。

问：rfq-market 的 K 线和 overview 各负责什么？

答：K 线负责历史 OHLCV 和统计数据；overview 里的当前价优先来自 SwapService 的 indicative quote，说明两者职责不是完全重叠的。

问：这三个仓库是不是完全同一版实现？

答：这个问题不要答死。更稳妥的说法是：它们属于同一 RFQ 业务线，但本地代码能看到接口存在代际差异，更像不同阶段实现。

8. 不要乱说的边界

  • 不要直接说“swap-engine 当前版本就直接驱动了 rfq_contracts_v2 新 Router 接口”。本地代码显示两边 ABI 存在代际差异。

1. 一句话定位

我负责的不是一个普通 WebSocket 推送接口，而是一条面向交易机会窗口的实时数据平面：从 Solana 多源事件接入、确定性新盘识别、低延迟优先级调度，到分阶段数据发布和链上置信度校正，在延迟、正确性与系统稳定性之间建立可量化的工程边界。

2. 30 秒回答

Delulu 里最有挑战的一次优化，是 Pump.fun 新盘的实时发现链路。它本质上不是“消息晚几秒”的体验问题，而是用户能否进入交易机会窗口的问题，所以我把它当成一套低延迟事件系统来设计。

我先把端到端延迟拆成数据接入、事件识别、业务补全和分发四段，并以尾延迟而不是平均值作为目标。架构上采用多 RPC 竞速接入和节点健康评分；识别到新盘后生成确定性事件 ID，进入独立的高优先级通道；第一阶段只推送可交易所需的最小事件，Token metadata、图标和统计数据异步补发，避免慢依赖进入关键路径。同时利用 Solana processed → confirmed 的置信度变化做二阶段校正，并通过优先级队列、admission control 和降级策略保证流量突发时优先保住新盘 discovery。最终我优化的不是一个函数，而是整条链路的 P99、抖动、故障隔离和可恢复性。

3. 2–3 分钟回答

Pump.fun 新盘是一个非常典型的 latency-sensitive 场景。普通行情晚一两秒，用户可能只是觉得页面慢；但新盘发现晚一两秒，用户面对的价格、流动性和交易竞争环境可能已经完全不同。所以我一开始就没有把它定义成“优化 WebSocket”，而是定义成“缩短从链上事实出现到用户获得可交易信号的 critical path”。

第一件事是建立 latency budget。我把端到端耗时拆成 T_ingest + T_detect + T_enrich + T_distribute，分别对应 Solana 事件接入、Pump 指令识别、Token 数据补全和用户分发。优化目标看 P95、P99 和 jitter，而不是只看平均耗时，因为真正影响用户的是偶发长尾。每个事件都携带 slot time、首次接收时间、识别完成时间和广播时间，能够快速判断长尾来自 RPC、解析、队列还是推送层。

第二件事是重构关键路径。入口不依赖单一 RPC，而是对多个数据源做 first-valid-response-wins，同时维护节点延迟、slot 落后和错误率评分，动态降低异常节点权重。事件进入系统后，使用 Pump Program 的指令、账户关系和关键字段做确定性识别，并以 slot + signature + instructionIndex 生成事件 ID，所以多节点重复上报、服务重试和消息重放都可以幂等合并。

第三件事是把“发现”和“补全”拆成两个阶段。第一阶段的 discovery event 只包含 Token mint、pair/bonding curve、创建者、slot、signature 和初始状态等交易决策真正需要的字段，识别完成后立即进入独立的高优先级通道；名称、图标、社交信息、持仓分布和风险标签则异步 enrichment，再通过同一个 event ID 做增量更新。这样 IPFS、metadata 服务或统计任务变慢时，不会污染首条新盘信号的关键路径。

第四件事是处理 Solana 的低延迟与确定性冲突。如果必须等到 finalized 再发，消息很可靠，但已经失去速度；如果只相信最早的 processed，又要承担 fork、节点视图差异和误报风险。我的设计是两阶段置信度：processed 时先发布低延迟 discovery，并明确标记 confidence；confirmed 后发送状态升级，异常情况下则发送 correction 或 tombstone。前端和下游不需要把早期信号误认为最终事实。

第五件事是保证极端流量下系统仍然“有选择地正确”。我把 discovery、confirmation、enrichment 和普通行情分成不同优先级；队列接近水位时，先暂停昂贵 enrichment、合并重复更新、降低非核心统计频率，最后才对普通低优先级事件做限流，但尽可能保住新盘发现和确认事件。系统不追求所有消息同等级服务，而是通过 admission control 明确保护最有业务价值的流量。

最终这次工作的价值，不只是减少了几个中间 hop，而是建立了一套低延迟事件平台的完整方法：有明确的延迟预算，有最小关键路径，有多源容灾和幂等，有链上置信度校正，也有过载时的业务优先级。即使后续接入其他 launchpad，这套模型也可以复用，而不是再为每个平台写一条临时推送链路。

4. 为什么这个问题难

延迟和链上确定性互相冲突

新盘业务希望尽可能接近 processed 状态发送，但越早的链上视图越可能受到节点差异、短暂 fork 或 RPC 延迟影响。真正的问题不是选择“快”或“准”，而是让事件携带置信度并支持后续状态升级和校正。

平均延迟没有意义，长尾才决定体验

系统平均很快，不代表交易用户真的获得了稳定优势。单个 RPC 抖动、metadata 超时、队列拥塞或 WebSocket 扇出都可能制造 P99 长尾，所以需要分段延迟预算和 per-event trace。

多源接入会带来重复、乱序和视图不一致

接入多个 RPC 可以降低单点抖动，但同一交易会被多次上报，不同节点看到的 slot 高度和 commitment 也可能不同。没有确定性事件 ID、slot watermark 和状态合并规则，多源反而会放大重复推送。

新盘流量具有突发性和高价值

热门时段可能短时间出现大量 Program 事件。系统不能简单地无限排队，也不能在过载时随机丢消息，必须知道哪些流量可以降级、哪些事件必须优先保护。

发现速度和数据完整度互相冲突

名称、图标、社交链接、持仓结构和风险标签都很有价值，但它们依赖链外或重计算服务。把完整信息放进第一条消息，会让最慢的 enrichment 决定整条链路的速度。

5. 原方案为什么不够

传统链路通常是：

单 RPC → 完整交易解析 → metadata/统计补全 → MQ → 通用 consumer → DB/cache → WebSocket

这个设计适合普通行情，但不适合机会发现：

  • 单 RPC 的抖动会直接成为系统抖动；
  • 所有业务共用一条队列，热点流量会产生 head-of-line blocking；
  • 等 metadata 全部成功才发布，最慢依赖决定首包延迟；
  • 只有一个 success 状态，无法表达 processed、confirmed 和 corrected；
  • 重复上报依赖临时缓存去重，服务重启或重放后仍可能重复推送；
  • 只优化平均耗时，无法解释为什么用户偶尔会晚很多。

单纯加机器、加 worker 或扩大队列也解决不了这些问题。它可能提升吞吐，却会掩盖长尾、放大积压，并把资源问题延后到下一层。

6. 核心设计与原理

端到端 latency budget

把用户感知延迟定义为：

T_total = T_ingest + T_detect + T_enrich-critical + T_queue + T_fanout

每一段都有独立指标和预算：

  • T_ingest：数据源观察到 slot 到系统首次接收；
  • T_detect：首次接收到确认 Pump Create；
  • T_enrich-critical：只计算首包必需字段；
  • T_queue：事件等待分发的时间；
  • T_fanout：广播服务接收到完成分发。

对外 SLO 以 P95/P99 为主，平均值只用于观察趋势。WebSocket 没有业务 ACK 时，系统边界应定义为“广播服务成功接受或写入连接”，不能把它包装成用户设备一定已经展示。

多源竞速与动态健康评分

多个 Solana 数据源并行接入，采用 first-valid-response-wins，而不是等待所有节点形成 quorum。后台持续计算：

  • 首包延迟；
  • 当前 slot 落后量；
  • 错误率和断连率；
  • 数据完整率；
  • 与主流节点视图的偏差。

健康节点保留高权重，持续落后的节点降权或熔断。这样既利用多源降低单点长尾，又避免慢节点持续制造过期事件。

Program-aware 确定性识别

不是看到 Token mint 就判断为新盘，而是解析 Pump Program 指令并校验关键账户关系，尽早产出结构化 discovery event。

事件 ID 使用稳定的链上坐标，例如：

eventId = hash(chainId, slot, signature, instructionIndex, eventType)

同一事件无论来自多少 RPC、被消费多少次或发生多少次任务重试，都映射到同一个 ID。下游按照 event ID 和状态版本幂等合并。

Discovery 与 enrichment 分阶段发布

第一阶段只发布交易决策最必要的信息：

  • mint；
  • pair 或 bonding curve；
  • creator；
  • slot 和 signature；
  • launchpad；
  • commitment/confidence；
  • event ID 和 version。

第二阶段异步补充：

  • Token name、symbol、icon；
  • 社交信息；
  • 初始流动性和市值；
  • holder concentration；
  • creator 历史；
  • 风险标签。

补充事件使用同一个 event ID 和更高 version。前端先展示机会，随后平滑补全，不需要等待所有慢依赖。

两阶段置信度与事件校正

事件状态可以设计为：

DISCOVERED(processed) → CONFIRMED → ENRICHED

异常分支：

DISCOVERED → REVOKED/CORRECTED

早期 discovery 是低延迟信号，confirmed 是更高置信度事实。下游按状态机更新，而不是把每条消息当成互不相关的新消息。

业务优先级与 admission control

将事件按业务价值分层：

  1. 新盘 DISCOVERED；
  2. CONFIRMED / REVOKED；
  3. 关键交易状态；
  4. metadata enrichment；
  5. 普通统计和非核心行情更新。

队列水位升高时按顺序降级：

  • 合并同一 event ID 的中间更新；
  • 暂停或延迟 enrichment；
  • 降低非核心统计刷新频率；
  • 限流普通事件；
  • 保留 discovery 和 correction 的最小处理能力。

这种策略的重点不是“绝不丢任何消息”，而是过载时仍能保证最重要的业务语义。

可观测性与回放

每个 event 都携带统一 trace context，核心指标包括：

  • RPC 首包延迟和 slot lag；
  • detect latency；
  • queue age；
  • P95/P99 end-to-end latency；
  • duplicate ratio；
  • correction/revocation ratio；
  • enrichment timeout ratio；
  • WebSocket fanout latency；
  • 各优先级队列水位。

可靠日志保存原始链上坐标和状态版本，服务重启后可以重放。下游依靠 event ID 幂等，因此回放不会变成重复的新盘通知。

7. 结果与业务价值怎么讲

可以这样收口：

我把 Pump.fun 新盘从一个普通消息推送功能，升级成了一条面向交易机会的实时数据平面。优化的核心不是无限加并发，而是缩短最小关键路径、把慢 enrichment 移出首包、用多源竞速降低 RPC 长尾、用确定性事件 ID 解决重复，并通过 processed 到 confirmed 的状态升级处理低延迟与链上确定性的矛盾。过载时系统还能按业务价值降级，优先保住 discovery 和 correction。

可以强调的工程价值：

  • 用户更早获得可交易信号，而不是等完整资料全部生成；
  • P99 和 jitter 可分段定位，不再只看平均耗时；
  • 单个 RPC、metadata 服务或普通行情队列不再直接拖慢新盘；
  • 多源重复、服务重放和下游重试通过事件 ID 幂等收敛；
  • 早期链上信号可以被确认或撤销，不把“快”伪装成“最终正确”；
  • 同一套 discovery/enrichment 模型可以扩展到其他 launchpad。

如果没有真实数据，不要编具体毫秒数。只有确实有监控依据时，才说“达到内部实时发现 SLO”或“显著降低长尾和抖动”，并准备说明 SLO 的定义、采样边界和监控方式。

8. 常见追问

问：为什么不等 confirmed 再推送？

答：

等 confirmed 更稳，但会直接消耗交易机会窗口。我把“是否发布”和“置信度多高”拆开：processed 时发布 discovery，并明确标记低置信度；confirmed 后升级状态；如果链上视图发生变化，则发送 correction 或 revoke。这样用户可以选择速度和风险，而不是系统替所有用户做同一个取舍。

问：多 RPC 会不会让重复和乱序更严重？

答：

会，所以多源接入必须和确定性事件 ID、slot watermark、版本状态机一起设计。first-valid-response 负责降低首包延迟，event ID 负责合并重复，slot 和 commitment 负责判断事件新旧，后续状态只能按允许的状态机升级，不能让晚到的旧消息覆盖 confirmed 状态。

问：为什么 metadata 不放在第一条消息里？

答：

第一条消息的目标是让用户尽早获得可交易事实，而不是一次返回完整详情。metadata、图片和风险统计往往依赖链外服务，也是长尾最大的部分。拆成 discovery 和 enrichment 后，慢依赖只影响展示完整度，不影响发现速度。

问：Kafka 还要不要？

答：

要，但它承担的是可靠日志、回放和普通业务消费，不应该让所有通用处理都串在首包 critical path 上。低延迟通道负责尽早发布，可靠日志负责重放和最终状态，二者通过 event ID 收敛。

问：流量突增时如何保证系统不雪崩？

答：

关键是优先级和 admission control，而不是无限扩容。系统先合并同一事件的中间版本，再暂停 enrichment、降低非核心统计频率、限流普通行情，始终为 discovery 和 correction 保留容量。每个队列都有水位、最大等待时间和降级阈值。

问：怎么证明优化真的有效？

答：

我会先固定测量边界，例如从首个健康 RPC 观察到事件，到广播服务接受 discovery 消息；然后按 ingest、detect、queue、fanout 分段记录，比较 P50、P95、P99、jitter 和超时比例。只说平均值下降不能证明交易用户的体验变稳定。

问：如果早期 discovery 最后被撤销怎么办？

答：

discovery 本身必须带 commitment 和 confidence，下游不能把 processed 当 finalized。确认失败时发送同 event ID 的 revoke/correction，并让前端明确展示状态变化。低延迟信号天然包含风险，系统要做的是让风险可表达、可校正，而不是假装不存在。

9. 表述边界

  • 不把“广播服务接受消息”说成“所有用户设备已经收到并展示”。
  • 不说多 RPC 可以消除所有分叉、延迟和数据差异。
  • 不说 processed 事件等同于最终链上事实。
  • 不说系统实现了端到端 exactly-once；更准确的是可靠日志加下游幂等。
  • 未真实上线的多源竞速、置信度状态机或 admission control，要表述为设计和演进方案。
  • 不编造毫秒数、P95/P99、吞吐量或提升百分比。

三、Delulu：限价单如何做到更快、更准确地触发

1. 一句话定位

我把限价单设计成事件驱动的分层触发链路：实时成交负责唤醒，只查询受影响的候选订单；用有界排序窗口改善消息乱序，用精确订单语义判断触发，再用状态机和链上交易追踪解决重复执行与最终结果不确定的问题。

2. 30 秒回答

限价单最难的不是写一个价格比较，而是同时处理触发延迟、成交消息乱序、订单规模、重复触发和链上执行失败。我们没有用低频 cron 扫全表，而是直接消费实时 trade 流，用 1 秒窗口按区块号整理消息；每批只保留受影响 pair 或 token 的最新有效价格，只查这些范围内的 waiting 订单，再按买入、卖出、止盈、止损的不同规则判断。订单创建时如果当前价已经满足条件，会走立即触发快路径。命中后进入异步执行，并通过 WAITING -> HANDLING 条件更新抢占订单，链上提交后再跟踪 tx 最终状态。这样快来自事件驱动和范围收缩，准来自顺序整理、业务语义和状态机，而不是单纯提高轮询频率。

3. 2–3 分钟回答

我在 Delulu 交易服务里遇到过一个典型的实时交易系统问题：用户希望限价单一到价格就尽快触发，但市场成交消息会乱序、重复到达，同一个 pair 可能有很多 waiting 订单，链上提交又不等于最终成功。

如果使用 cron 每隔几秒扫一次所有订单，延迟下限就是扫描周期，而且订单越多，数据库压力越大。如果每来一笔成交就直接查询和执行，又会被高频消息放大，还可能因为乱序价格或重复消息多次触发同一订单。

我的处理思路是把“收到市场信号、判断订单、执行交易、确认链上结果”拆成四层。第一层直接消费 market 的实时 trade 流，避免低频轮询。消息先进入一个 1 秒有界窗口，再按 BlockNum 排序，改善跨消息乱序。第二层在一个批次里只保留每个 pair 或 token 的最新有效成交，只查询这些受影响范围内、状态为 waiting 且订单类型匹配的候选订单，避免全表扫描。第三层按订单语义判断：买入限价是当前价低于限价时触发，卖出限价和止盈是当前价高于阈值时触发，止损则相反。创建订单时还会拿当前 pair 价格判断一次，如果已经满足条件，立即进入执行任务，不需要等下一条行情。

第四层是异步执行和状态机。触发线程只 enqueue Asynq 任务，真正执行前通过数据库条件更新把状态从 WAITING 改成 HANDLING，只有抢到状态的 worker 才能继续，避免重复任务造成重复交易。执行时重新获取 pair 信息和用户交易配置，计算 amountOutMin 后提交链上；拿到 txHash 后进入 CHAIN_PENDING，由独立任务轮询交易状态，成功才标记完成，明确失败则退回 waiting。连续错误通过 Redis 做指数退避，避免坏订单持续占用资源。

这个方案的取舍也很明确。1 秒排序窗口会增加最多一个窗口的等待，但提高了跨区块消息顺序的稳定性；只按区块号排序无法保证同一区块内的完整交易顺序，所以我不会把它说成严格的全序。执行前虽然会重新获取 pair 信息来计算交易参数，但当前代码没有再次调用触发规则，因此也不能说成“提交前二次确认价格仍满足条件”。更准确的说法是：它提升了触发时效、候选筛选准确性和重复执行控制，最终成交仍然受链上价格、滑点和交易状态影响。

4. 为什么这个问题难

快和准天然冲突

完全不等待、每条消息立即判断，延迟最低，但更容易受到乱序和重复消息影响；为了等到绝对完整的顺序再判断，又会错过最佳交易时机。

触发和成交不是一回事

“价格达到阈值”只说明可以发起执行，不代表链上必然成交。RPC、余额、gas、路由、滑点、MEV 和链上回执都可能改变最终结果。

同一个订单可能被多次看见

一个价格区间内可能连续出现多笔满足条件的成交，多实例 consumer 或重试任务也可能同时处理同一个订单。没有原子状态抢占，就可能重复发交易。

不同订单不能共用一条比较规则

买入限价、卖出限价、止盈和止损的触发方向不同；如果只写成一个通用“大于等于”判断，很容易出现业务语义错误。

5. 原方案为什么不够

低频扫表

定时器 → 查询全部 waiting 订单 → 获取当前价格 → 逐个判断

这个方案的问题是：

  • 触发速度受扫描周期限制；
  • 数据库压力随订单总量增长；
  • 大部分订单对应的 pair 根本没有产生新成交，却被重复检查；
  • 扫描和执行耦合后，一批慢订单会拖慢下一批。

每条成交立即同步执行

这个方案虽然表面上快，但会导致：

  • 高频行情直接放大数据库查询；
  • 乱序和重复成交更容易重复触发；
  • RPC 和链上交易阻塞 consumer；
  • 执行失败会影响后续行情消费。

6. 核心设计与原理

事件驱动触发

trade 服务消费市场实时成交事件，不依赖低频 cron 扫描。只有 pair 或 token 真正出现新成交时，相关订单才进入判断范围。

快的第一层原因不是“机器更强”，而是从轮询模型改成事件唤醒模型。

1 秒有界乱序窗口

consumer 先把 trade 放进 buffer，每秒复制并清空一次，再按 BlockNum 排序后处理。

它解决的是“改善跨消息、跨区块乱序”，不是构造严格全序：

  • 能让较小区块号的成交优先被处理；
  • 增加最多一个窗口的等待；
  • 同一区块内如果没有 transaction index 或 log index，仍不能知道严格先后。

因此面试中可以说“提高顺序稳定性”，不能说“完全解决所有乱序”。

候选范围收缩

一个批次先构造：

  • pair → latest trade；
  • token → latest trade。

然后只查询：

  • 当前 chain；
  • 状态为 WAITING；
  • pair 或 token 位于本批受影响范围；
  • order type 位于本次需要处理的类型。

这把查询复杂度从“所有 waiting 订单”收缩到“刚刚发生价格变化的订单集合”。这是快的第二层原因。

精确触发语义

代码中的比较关系是严格不等式：

  • 买入限价：currentPrice < limitPrice；
  • 卖出限价：currentPrice > limitPrice；
  • 止损：currentPrice < limitPrice；
  • 止盈：currentPrice > limitPrice。

price == limitPrice 在当前实现中不会触发。面试时不要随口说成“小于等于”或“大于等于”。

创建时快路径

创建限价单完成后，系统会重新获取当前 pair 信息并调用 IsTriggeredLimit。如果下单当下已经满足条件，直接创建 LimitOrderFillTask，不等待下一笔市场成交消息。

这解决了一个容易忽略的竞态：用户提交订单前价格已经越过阈值，但之后短时间没有新 trade，如果只依赖事件流，订单会一直等到下一条事件才被唤醒。

触发与执行解耦

判断命中后只创建 Asynq 任务，不在 Kafka consumer 中同步发链上交易。这样：

  • RPC 变慢不会阻塞市场消息消费；
  • 执行可以独立扩容和重试；
  • 触发时间与最终成交时间能够分别观测。

原子状态抢占

worker 执行前使用带条件的数据库更新：

UPDATE ... SET status = HANDLING WHERE id = ? AND status = WAITING

只有真正修改到一行的 worker 才获得执行权。即使同一个订单被多个成交事件命中、产生多个任务，也只有一个任务能从 WAITING 抢到 HANDLING。

这保证的是“订单状态层面的单一执行者”，不是整个分布式消息系统严格 exactly-once。

最新执行参数与滑点保护

执行任务会重新获取 pair 信息和用户交易配置，用最新的 token、base token、decimals、路由和 slippage 计算 amountIn 与 amountOutMin。

这里要准确表述：

  • 它会刷新执行参数；
  • 它会基于限价和当前 pair 信息计算最低输出；
  • 当前代码不会在发交易前再次调用 IsTriggeredLimit；
  • 因此不能包装成“二次验价不满足就取消执行”。

链上状态闭环

交易提交成功只代表拿到 txHash，订单进入 CHAIN_PENDING。独立 tx tracker 每 3 秒查询链上状态，最长跟踪 3 分钟：

  • 成功：订单标记为 SUCCESS；
  • 明确失败：清空 txHash 并退回 WAITING；
  • 普通执行错误：HANDLING 退回 WAITING；
  • 连续错误：Redis 记录错误次数并指数增加下次重试间隔，最长一天；
  • 长时间未成交：订单过期，避免永久消耗系统资源。

7. “更快”和“更准”分别来自哪里

更快：

  • 实时 trade 事件唤醒，不等 cron 周期；
  • 只查询受影响 pair/token，不扫全表；
  • 订单创建时有立即触发快路径；
  • 触发和链上执行解耦，consumer 不被 RPC 阻塞。

更准：

  • 1 秒窗口和 BlockNum 排序改善跨消息乱序；
  • 一个批次过滤零价格并选取相关 pair/token 的有效成交；
  • 按订单类型执行不同的严格比较规则；
  • WAITING -> HANDLING 原子抢占避免重复执行；
  • 链上结果单独跟踪，不把“已提交”误判为“已成交”。

这里的“准”是触发语义、候选范围和状态判断更准确，不等于保证按用户看到的价格成交，也不等于没有滑点。

8. 结果与取舍怎么讲

可以说：

我把限价单从低频全量扫描思路改成了实时成交驱动，只处理价格发生变化的 pair 和 token，并增加创建时快路径，所以触发延迟和无效查询都会下降。为了控制乱序，我接受了一个 1 秒有界窗口；为了避免重复执行，用数据库条件更新抢占状态；为了区分提交和成交，又把链上 tx tracking 单独做成状态闭环。

需要主动承认：

  • 1 秒窗口会引入有界延迟；
  • 只按区块号排序不能保证同一区块内全序；
  • trade 事件流中断时，纯事件触发链路也会受影响；
  • 当前执行前不会再次判断是否仍满足触发条件；
  • 链上成交价格仍受滑点、流动性和区块环境影响。

9. 常见追问

问：为什么不用 Redis 分布式锁防止重复执行？

答：

这里订单状态本身就在数据库里，所以我用条件更新把状态流转和抢占执行权放在一个原子操作里。Redis 锁如果超时或续期失败，还要处理锁状态和订单状态不一致；数据库 WAITING -> HANDLING 更贴合订单事实。Redis 在这里主要用于记录错误次数和下一次重试时间。

问：为什么要等待 1 秒，不是越快越好吗？

答：

如果完全不做整理，跨 partition 或跨批次乱序会让较旧价格在较新价格之后到达，增加误触发和重复判断。1 秒是一个有界取舍：接受小段等待换取更稳定的区块顺序。它不是严格全序，同一区块仍然需要更细粒度的 transaction/log ordinal 才能完全排序。

问：订单触发后，价格又回去了怎么办？

答：

当前实现的语义是“成交事件满足条件就创建执行任务”，执行阶段会刷新 pair 信息和交易配置，用限价与 slippage 计算 amountOutMin，但不会再次调用触发判断。如果最终报价达不到最低输出，链上交易应当失败或不成交。不能把当前实现说成提交前会二次撤销触发。

问：如果同一个订单产生了多个任务呢？

答：

多个任务都可以到达 worker，但只有第一个成功把状态从 WAITING 改成 HANDLING 的任务能继续。其他任务更新不到记录，会直接退出。

问：为什么交易失败又退回 waiting？

答：

限价条件后面仍可能再次成立，链上失败不一定意味着订单业务上永久失效。退回 waiting 可以重新等待市场信号，但连续失败会指数退避，避免坏订单高频重试。

10. 表述边界

  • 不说“严格按链上最终成交顺序触发”。
  • 不说“执行前一定会二次确认价格”。
  • 不说“限价单保证以限价成交且零滑点”。
  • 不说“消息和执行都是 exactly-once”。
  • 不编造固定毫秒级触发延迟。

四、ARH RFQ：多方参与下如何建立合约信任边界

1. 一句话定位

RFQ 最复杂的不是写一个 swap，而是同时约束用户、Relayer、平台、Maker、Settlement 和可插拔 Vault：每一方只能行使本次报价明确授予的权限，任何一方都不能通过篡改参数、重放签名、滥用 callback 或虚报输出转移用户资产。

2. 30 秒回答

RFQ 合约里我遇到的最大挑战，是参与方很多，而且它们的信任边界不同。用户授权资金，Relayer 代发交易，平台控制报价准入和费用，Maker 对实际报价负责，Vault 又是可插拔的外部执行器。

我们用 Permit2 witness 把用户的资金许可和本次 RFQ 的业务参数绑定，Router 必须根据真实 calldata 重建 witness，Relayer 改收款人或最低输出都会导致验签失败；Maker 和平台分别做两层 EIP-712 签名；Settlement 再校验 deadline、executor、fee、partial fill 和 bitmap nonce。调用 Vault 时只通过 transient context 发放一次性、精确金额的 callback 权限，最后不信任 Vault 返回值，而是用用户真实余额增量判断输出。这样任何一层失败都会在同一笔 EVM 交易里原子回滚。

3. 2–3 分钟回答

这套 RFQ 的业务模式是链下由做市商给出报价，用户把签名报价带到链上结算。表面上像一次 swap，但实际同时存在多个独立主体：用户拥有输入资产，Relayer 可能替用户发交易，平台决定哪些报价能进入系统并收取多少费用，Maker 对报价内容负责，Vault 负责最终换币或资产交付。

最难的问题是，不能因为某个签名合法，就默认整笔交易符合所有人的意图。例如，普通 Permit2 签名可以证明用户允许转一定数量的 Token，但在 Relayer 场景下，如果没有绑定收款地址、输出币种和最低输出，Relayer 仍可能拿着合法签名提交一笔被篡改的交易。

所以第一层是用户授权边界。Relayer 路径强制使用 Permit2 witness，witness 绑定 from、to、inputToken、outputToken、amountIn、amountOutMin、deadline。Router 不直接相信调用方传来的 witness，而是用本次真实 calldata 重新计算，再交给 Permit2 验证签名、nonce 和 deadline。这样只要 Relayer 修改核心业务参数，签名摘要就会变化。

第二层是报价授权。Maker 对 MMQuote 的 Vault、executor、输入输出 Token、数量、deadline、nonce 和 extraData 等字段签名；平台再对报价哈希和 fee 规则签名。两层签名分别表达“Maker 确实愿意按这份条件成交”和“平台允许这份报价进入结算并按这个规则收费”，不能互相替代。

第三层是不可信外部执行器。Settlement 会调用库存、V3 或 Ondo 等不同 Vault，但不会给 Vault 长期、无限的资金权限。它先把当前 Vault、payer、inputToken 和本次精确金额写入 transient storage；callback 只允许当前 Vault 调用，而且先清空上下文再转账，使这次权限只能使用一次。Vault 执行完成后，Settlement 也不相信它返回的 amountOut，而是比较接收方调用前后的 Token 余额差。

最后还有重放和价格保护。Maker nonce 用 bitmap 管理，执行后整个位被消费；deadline 限制报价有效期；partial fill 和 time decay 决定本次最低输出；Settlement 做单腿校验，Router 再做聚合 amountOutMin 校验。任一签名、nonce、callback 或余额差不符合要求，整笔 EVM 交易回滚，已经扣的 fee、写入的 nonce 和资产转移也会一起恢复。

这个案例我会强调，真正的难点不是某一个加密 API，而是先画清楚每个主体能相信什么、不能相信什么，再用签名域、一次性 nonce、callback capability 和真实余额变化把信任边界落实到代码。

4. 为什么这个问题难

资金所有者和交易发起者可能不是同一个人

用户签名，Relayer 提交交易并支付 gas，意味着 from != msg.sender。合约不能再用“调用者就是资产所有者”的简单假设。

一个签名无法表达所有主体的授权

用户授权 Token，Maker 承诺报价，平台批准准入和费用。这三类意图不同，不能混成一个签名，也不能让平台替 Maker 承诺资金。

Vault 是外部调用和重入边界

Settlement 要支持多类 Vault，但不能假设 Vault 一定诚实。Vault 可能重复 callback、超额拉取输入 Token，或者返回一个虚假的 amountOut。

RFQ 既支持聚合，又要保证每一腿安全

Router 可以组合多条 quote。只校验总输出可能掩盖某一腿异常，只校验每腿又不能替代用户对整笔交易的最低输出要求。

5. Permit2 是做什么的

传统 ERC20 approve 的问题

普通 ERC20 交易通常是：

  1. 用户先调用 Token 的 approve(router, amount)；
  2. Router 再调用 transferFrom(user, router, amount)。

如果每换一个 Router 都做长期授权，用户要多发一笔链上交易，也容易留下过大的 allowance。

Permit2 的作用

Permit2 可以理解为一个通用授权中间层：

  1. 用户通常先把 Token allowance 授权给 Permit2 合约；
  2. 后续针对具体 spender、Token、金额、nonce 和 deadline，在链下签名；
  3. Router 把签名交给 Permit2；
  4. Permit2 验证签名和防重放条件后，从用户地址把精确数量的 Token 转到目标位置。

它减少的是“每个业务 Router 都单独做长期 approve”的需求，不是完全不需要任何 ERC20 approve。用户第一次通常仍要把 Token 授权给 Permit2。

普通 Permit 为什么还不够

普通 Permit2 签名主要解决“谁能在什么时候转多少 Token”。但 RFQ 还包含业务意图：

  • 最终收款人是谁；
  • 用户想换成什么 Token；
  • 最少要收到多少；
  • 这笔 RFQ 什么时候失效。

如果 Relayer 只拿到普通 Token 转账授权，而这些业务参数没有进入签名，可能出现“签名是真的，但调用不是用户原本同意的那一笔”。

Permit2 witness 的原理

witness 是附加在 Permit2 授权中的一段 EIP-712 结构化业务数据。当前 RFQ witness 绑定：

  • from；
  • to；
  • inputToken；
  • outputToken；
  • amountIn；
  • amountOutMin；
  • deadline。

Router 根据实际函数参数重新计算 witness hash，而不是相信 Relayer 提供的 hash。Permit2 最终验证的是“Token 转账许可 + 这段业务 witness”的组合摘要。

如果 Relayer把 to 从用户地址改成自己的地址，或把 amountOutMin 调低，Router 重算出的摘要就会和用户签名时的摘要不同，验签失败。

Permit2 witness 的边界

  • 当前 witness 不包含完整 RFQ quote 数组。
  • 完整报价内容由平台签名和 Maker 签名继续保护。
  • Relayer 是代付 gas 和提交交易，不应直接包装成所有场景下的 gasless。
  • 原生 ETH 路径和 ERC20 Permit2 路径不能混为一谈。

6. 双层 EIP-712 签名为什么需要

Maker 签名

Maker 对 MMQuote 签名，核心包括：

  • 使用哪个 Vault；
  • 允许哪个 executor 执行；
  • 输入、输出 Token；
  • 输入、输出数量；
  • deadline；
  • nonce；
  • extraData。

它证明的是：Maker 确实愿意按这份报价和执行方式成交。

平台签名

平台再对 MMQuote 的结构化哈希以及 feeTo / feeRate 等规则签名。

它证明的是：平台已经接受这份报价进入系统，并认可对应收费规则。

为什么不能只保留一个

  • 只验平台签名：平台等于替 Maker 对资金和报价作承诺。
  • 只验 Maker 签名：Maker 可以绕过平台准入、费用和风控规则。

两层签名把“资产与报价承诺”和“平台准入与费用授权”解耦。

7. Settlement 如何约束不可信 Vault

一次性 callback 权限

Settlement 在调用 Vault 前，把下面的信息写入 transient storage：

  • 当前被允许 callback 的 Vault；
  • payer；
  • inputToken；
  • 本次净输入金额。

Vault callback 时，Settlement 检查 msg.sender 必须是当前 Vault。校验通过后先清空 transient context，再执行精确金额转账。

“先清状态、后转账”遵循 checks-effects-interactions 思路，即使 Token 转账过程发生外部交互，原 callback capability 也已经失效，不能被重复使用。

为什么使用 transient storage

transient storage 只在当前交易生命周期内存在，交易结束自动清空，适合保存一次 swap 的临时授权上下文。相比永久 storage：

  • 不需要长期保存临时状态；
  • 不会把 callback 权限残留到下一笔交易；
  • 读写成本更适合这种短生命周期数据。

边界是执行环境需要支持 Cancun/EIP-1153。

为什么不信任 Vault 返回值

恶意或异常 Vault 可以返回一个很好看的 amountOut，但这不代表用户真的收到 Token。

Settlement 的做法是：

  1. 调用前记录接收方 outputToken 余额；
  2. 调用 Vault；
  3. 调用后再次读取余额；
  4. 使用余额差作为真实 amountOut。

这样结算依据是实际资产变化，而不是外部合约自报的数字。

8. nonce、partial fill 和 time decay

Bitmap nonce

Maker nonce 使用 bitmap 管理。可以把它理解成：

  • 一个大整数按位表示很多 nonce 是否已经使用；
  • 每个报价对应一位；
  • 成交时把对应位设为已使用；
  • 再次使用相同 nonce 会失败。

优点是批量存储和取消多个 nonce 更节省 gas。

需要注意：报价即使只做了一次 partial fill，当前设计也会消费整个 nonce，剩余部分不能继续拿同一签名反复成交。

Partial fill

Settlement 允许在规则范围内按比例成交，但会根据实际 fill 比例重新计算输出要求，并限制过低的 fill。它解决的是流动性和实际成交量不一定完全等于原报价的问题，不代表可以无限拆分重复成交。

Time decay

链下报价到真正上链之间有时间差。time decay 根据报价参数和经过时间调整可接受输出，使报价对短期市场变化有明确、可验证的衰减规则，而不是由 Relayer 临时修改。

9. 输出和原子性保护

输出保护分两层：

  • Settlement 校验每条 RFQ 腿的真实到账；
  • Router 校验所有腿聚合后的总输出不低于用户的 amountOutMin。

任意一项校验失败都会 revert。同一 EVM 交易中已经发生的：

  • fee 转移；
  • nonce 消费；
  • Permit2 转账；
  • Vault 内部操作；

也都会一起回滚。

这里可以说“单笔 EVM 交易内部原子”，不要扩展成链下报价服务和链上执行之间也存在分布式事务。

10. 常见追问

问：Permit2 是不是完全不用 approve？

答：

不是。用户通常仍要先给 Permit2 一次 ERC20 allowance。它主要避免用户为每个业务 Router 分别保留长期授权，并支持用链下签名表达单次或受限的转账许可。

问：为什么 Relayer 必须用 witness？

答：

因为资金所有者和调用者分离后，只验证 Token、金额和 deadline 不足以证明整笔 RFQ 符合用户意图。witness 把收款人、输入输出 Token、amountOutMin 等业务参数也放进签名，Relayer 无法拿合法 Token 授权去提交另一笔业务参数不同的交易。

问：witness 为什么不直接绑定所有 quotes？

答：

当前实现把用户级交易意图和完整报价授权分层处理：witness 绑定用户最关心的收款、Token、金额和最低输出；完整报价分别由平台签名和 Maker 签名保护。代码里虽然存在 quote hash 能力，但当前 Router witness 路径没有把完整 quote 数组纳入。

问：为什么 callback 自己不一定需要再加一层 nonReentrant？

答：

callback 的 capability 由 transient context 限制，只允许当前 Vault，并且使用前先清空。外层 settle 仍需要保护整个结算流程；callback 的重点是一次性、精确金额授权。如果简单在外层和 callback 同时套不可重入锁，合法的嵌套 callback 反而可能无法执行。

问：Vault 执行失败后，fee 和 nonce 会不会已经被消耗？

答：

不会永久消耗，因为这些动作都在同一笔 EVM 交易里。后面的 Vault 或最低输出校验 revert 时，前面的状态写入和 Token 转账也会一起回滚。

11. 表述边界

  • 不说“Permit2 完全不需要 approve”。
  • 不说“witness 已绑定完整 RFQ quote 数组”。
  • 不说“平台签名可以替代 Maker 签名”。
  • 不说“信任 Vault 返回的 amountOut”。
  • 不说“partial fill 后剩余报价可继续复用同一个 nonce”。
  • 不说“链下报价和链上结算是一个分布式原子事务”。

五、Anchored：如何让 Fund Transfer 稳定完成复杂异步资金流程

1. 一句话定位

我没有把跨 Cashier、Gateway、Alpaca、Broker 和跨链协议的资金流程包装成一个无法实现的分布式事务，而是把它设计成可持久化、可重入、幂等、可对账的状态机，让系统在超时、重启、事件延迟和跨链 pending 后仍能从最后一个确定状态继续推进。

2. 30 秒回答

Anchored 里最有挑战的是 Fund Transfer。一笔提现可能经过 Cashier、Gateway、Alpaca journal、资产 swap、Broker withdrawal、Across 或 CCTP 跨链以及最终链上结算，任何接口超时都可能是“实际成功但响应丢了”。如果直接重试，可能重复下单、重复提现或重复发链上交易。

我的方案是把流程拆成 Transfer 当前状态和 Step 审计记录，每个外部副作用步骤都持久化 client id、txHash、状态和等待原因；重试前先 query-before-create，链上 tx pending 时只等待，明确失败才生成新 attempt。单笔 Transfer 用分布式锁串行推进，后台定时重驱动 pending 流程；Across 用 depositId 对源链和目标链事件，CCTP 对 attestation、receiveMessage 和 nonce，最后再以 Gateway consumed 状态完成账实对账。这样实现的是可恢复的最终一致性，不是跨系统 exactly-once。

3. 2–3 分钟回答

Anchored 的 Fund Transfer 是我认为最适合讲的复杂异步问题。一笔非即时提现并不是一次数据库更新，它可能经过 Cashier 收集资金、Gateway 建立 operation、Alpaca OM journal、资产 swap、Broker withdrawal，再通过 Across 或 CCTP 跨链，最后由链上 CashSettler 和 Gateway 完成确认与消费。

这里最危险的异常不是接口明确返回 failed，而是状态不确定。例如调用 Alpaca 超时，外部订单可能已经创建；链上 RPC 超时，交易可能已经广播；源链 bridge tx 成功，也不代表目标链已经到账；服务还可能在拿到外部成功结果之后、写本地数据库之前崩溃。

如果只用一张主表加一个 processing 状态，失败后从头重试，会造成重复 journal、重复 swap、重复提现或重复链上交易，而且运维只知道“卡住了”，不知道卡在哪一层。

我的方案是把模型拆成三层：Operation 表示用户视角的一次资金操作；Transfer 保存当前推进状态；Step 保存每一次外部交互的审计事实。流程按 Collected、AlpacaOmJournal、AlpacaSwap、BrokerRequest、Processed、Bridge、Confirmed、Consumed 等步骤推进。每个涉及外部副作用的关键步骤都必须满足两个原则：执行前检查本地和外部事实，执行后立即保存可以恢复的标识。

对 Alpaca 和 Broker，我使用确定性的 client id，重试时先查询外部系统是否已经存在，再决定是否创建。对链上交易，拿到 txHash 后立即持久化；后续看到 receipt pending 就继续等待，只有明确 failed 才清理并重试。每笔 Transfer 用 Redisson 锁保证同一时间只有一个推进者，后台任务周期性重新发布 pending transfer，使服务重启后也能从数据库状态继续执行。

跨链不能只看一个 txHash。Across 要通过 depositId 关联源链 FundsDeposited 和目标链 FilledRelay；CCTP 要等待 attestation 和目标链 receiveMessage。如果 nonce 已经被消费，说明 receive 可能已由另一个执行者完成，但这还不等于整笔 Transfer 完成，系统仍要读取 Gateway 的 consumed 状态做最终对账。

这个设计把一个不可控的长事务，变成了可观察、可重入、可对账的最终一致性状态机。它的代价是状态和审计模型更复杂，而且不能承诺所有异常都自动反向补偿；但相比盲目重试，它能显著降低重复资金副作用，并让每一个 pending 都有明确原因和恢复路径。

4. 为什么这个问题难

没有全局事务

数据库、Broker API、Alpaca、Across、CCTP 和 EVM 链不共享同一个事务管理器。任何“全部成功或全部失败”的假设都不成立。

超时不是失败

外部请求超时只代表本地没有收到确定结果：

  • journal 可能已经创建；
  • swap order 可能已经成交；
  • withdrawal 可能已经受理；
  • 链上交易可能已经广播。

如果把 timeout 直接当 failed 并重新执行，最容易造成重复资金动作。

源端成功不等于资金流程完成

  • Broker 接受 withdrawal 不等于链上到账；
  • 源链 bridge tx 成功不等于目标链到账；
  • 目标链 receive 完成不等于 Gateway 已经 confirm；
  • Gateway confirm 不等于资金已被最终 consumed。

服务随时可能重启

内存中的“执行到第几步”不可靠。每一步必须能够从持久化事实重新判断：继续等、已经完成、明确失败，还是需要重新发起。

5. 原方案为什么不够

天真模型通常是：

transfer.status = PROCESSING → 顺序调用所有外部服务 → transfer.status = SUCCESS

它会遇到四类问题：

  • 中间失败后，不知道从哪一步恢复；
  • 外部成功、本地未落库时，重试可能重复执行；
  • 一个 PROCESSING 无法表达到底在等 Alpaca、Broker、bridge 还是链上事件；
  • 为了恢复而从头重跑，会重复产生不可逆的资金副作用。

另一个常见误区是为每一步都写一个“失败就反向调用”的补偿。资金系统中并不是所有外部动作都可以安全撤销，例如已经成交的 swap 或已经被目标链消费的跨链消息，不能假设存在通用回滚。

6. 三层状态模型

Operation：用户视角

表示用户发起的一次充值、提现或资金操作，回答“用户要做什么”。

Transfer：调度视角

保存当前处理到了哪个阶段、整体是否 pending、success 或 failed，回答“下一次后台任务应该从哪里继续”。

Step：审计和恢复视角

记录每个阶段的外部事实，例如：

  • 外部 client id；
  • provider order id；
  • txHash；
  • retry attempt；
  • wait reason；
  • provider response；
  • 当前 step 状态。

Transfer 提供快速调度，Step 提供历史证据。不能只保留后者，也不能只保留一个总状态。

7. 可重入推进与幂等控制

单 Transfer 串行化

处理一笔 Transfer 前先获取 Redisson 锁，避免定时任务、消息回调和人工重试同时推进同一笔资金流程。

分布式锁只解决“同一时间少一些并发执行者”，不单独承担资金幂等。真正的幂等还要依靠状态条件、确定性 client id 和外部事实回查。

Query-before-create

对 journal、swap order 和 Broker withdrawal 等外部 API，使用确定性的 client id：

  1. 根据 Transfer 和 attempt 构造稳定 client id；
  2. 重试前先用 client id 查询外部系统；
  3. 已存在则复用外部结果；
  4. 明确不存在才创建；
  5. 明确失败后才增加 attempt，生成新的 client id。

这解决“请求成功但响应丢失”问题。简单使用随机 UUID 会让每次重试都看起来像一笔新业务，无法判断是否重复。

链上 txHash 恢复

链上调用拿到 txHash 后立即保存。后续处理遵循：

  • receipt pending：保持当前 step，继续等待；
  • receipt success：推进下一步；
  • receipt failed：记录失败，必要时清理 txHash 并创建新的 attempt；
  • 本地状态落后：通过链上事件或合约状态修正。

这里仍有一个真实边界：交易已发出、txHash 还没成功持久化时服务崩溃。系统需要结合确定性业务标识、发送账户 nonce、链上事件或外部查询恢复，不能声称这个窗口天然不存在。

周期性重驱动

pending 不是错误终态。后台任务会周期性扫描并重新发布未完成 Transfer 的 process signal。每个 handler 必须可重入：

  • 已完成的 step 直接跳过；
  • pending 的外部动作只查询，不重发；
  • 明确失败才进入下一次 attempt；
  • 条件成熟后继续推进。

8. 跨链状态怎么判断

Across

Across 不能只看源链交易是否成功。完整判断至少包含：

  1. 源链出现 FundsDeposited；
  2. 解析并保存 depositId；
  3. 在目标链找到对应的 FilledRelay；
  4. 确认目标资产已经到达预期接收方；
  5. 再推进 Gateway confirm 和 consumed。

depositId 是连接源链存款和目标链填充的业务关联键。

CCTP

CCTP 的流程包括：

  1. 源链 burn；
  2. Iris attestation 可用；
  3. 目标链提交 receiveMessage；
  4. 目标链确认消息已被消费；
  5. Gateway 继续完成 confirm 和 consumed。

如果提交 receiveMessage 时发现 nonce 或 attestation 已经使用，不能直接当成失败重发。它可能意味着另一个执行者已经完成目标链 receive，此时应查询链上事实并把当前 step 对账为完成。

但“CCTP message 已消费”只代表跨链 receive 完成，不代表整笔 Fund Transfer 已成功。最终仍要以 Gateway 的 consumed 状态完成业务对账。

9. 可观测性和恢复

资金系统中的 pending 必须是可解释的。Step extra 中应能回答：

  • 正在等哪个外部系统；
  • 上一次请求使用什么 client id；
  • 是否已经拿到 txHash；
  • receipt 是 pending 还是 failed；
  • bridge 卡在源链、attestation、目标链还是 Gateway；
  • 已经重试多少次；
  • 下一次重试会查询还是重新提交。

这样告警不只是“Transfer 超时”，而是“某笔 Transfer 在 CCTP attestation 等待超过阈值”或“Broker withdrawal 已受理但 txHash 长时间未出现”。

10. 结果与取舍怎么讲

可以说：

我把原本跨多个外部系统的一次长事务，拆成可持久化的 step 状态机。每个外部副作用都有可恢复标识，重试先查询事实，链上 pending 不盲目重发，跨链同时核对源端和目标端，最终再用 Gateway consumed 状态收口。这样服务重启、消息延迟和接口超时后，系统都能从最后一个确定状态继续推进。

它带来的价值：

  • 降低重复 journal、swap、withdrawal 和链上交易风险；
  • pending 流程可重启恢复；
  • 外部成功但本地状态落后时可以对账修正；
  • 每个等待阶段可审计、可告警；
  • 业务主状态和外部执行事实不再混在一个字段里。

需要主动承认：

  • 这是最终一致性状态机，不是跨系统原子事务；
  • 不能承诺跨系统 exactly-once；
  • 不是所有步骤都存在自动反向补偿；
  • 发送外部请求和本地持久化之间仍可能存在崩溃窗口；
  • 提高可靠性的代价是状态模型、审计数据和运维逻辑更复杂。

11. 常见追问

问：为什么不使用分布式事务？

答：

参与方包含第三方 Broker、Alpaca、跨链协议和公链，它们不支持同一个两阶段提交协议。强行包装成分布式事务不现实。更合适的是持久化状态机、幂等外部调用、重试前查询和最终事实对账。

问：分布式锁能保证不重复提现吗？

答：

不能单独保证。锁只能减少同一时刻的并发推进，进程可能在外部成功后、释放锁前或落库前崩溃。真正的防重依赖确定性 client id、query-before-create、数据库状态和外部事实回查。

问：为什么超时后不直接重试？

答：

因为 timeout 是 unknown，不是 failed。直接重试可能重复产生不可逆副作用。应该先用 client id、order id、txHash 或链上事件查询原请求是否已经成功，明确不存在或失败后才创建新 attempt。

问：源链 bridge tx 成功为什么还不能结束？

答：

源链成功只证明资金进入 bridge。还要确认目标链 relay 或 receive 完成，然后由 Gateway confirm，最终到 consumed 才代表业务流程收口。

问：服务重启后怎么继续？

答：

当前 Transfer 状态和每个 Step 的 client id、txHash、等待原因都在数据库里。后台任务重新扫描 pending Transfer，handler 先判断步骤是否已经完成或仍在等待，再决定查询、推进或创建新 attempt，不依赖内存上下文。

问：失败后怎么补偿？

答：

先区分可重试、可对账和确实需要人工处理的失败。并不是所有资金动作都能自动逆向，例如已成交 swap 或已消费的跨链消息。系统重点是避免重复副作用、准确停在失败 step，并保存足够事实做后续补偿，而不是承诺通用自动回滚。

12. 表述边界

  • 不说“实现了跨系统分布式事务”。
  • 不说“所有外部调用严格 exactly-once”。
  • 不说“任何异常都会自动补偿”。
  • 不把源链 tx 成功说成跨链到账。
  • 不把 CCTP nonce 已消费说成整笔 Fund Transfer 已完成。
  • 不编造资金成功率、平均耗时或故障恢复指标。

  • 负责 RWA 交易系统 Indexer 与出入金链路建设，设计链上事件索引框架、资金 current-state / step 审计表、fund transfer 异步状态机，支持多链事件同步、非 instant 出入金批量归集、buffer 水位重平衡、跨链 bridge、Alpaca/Broker 外部流程、失败重试和对账追踪。

二、30 秒项目讲法

我在这个项目主要负责 indexer 和 fund transfer 出入金链路。

Indexer 这块不是简单扫链，而是 WebSocket 实时监听新区块，HTTP 轮询兜底，先把原始 event log 入库，再用 contractType + topic0 分发到不同 handler，解析成订单、余额、cash operation、fund transfer 等业务表。这样做的好处是可断点续跑、可排查、可重放。

Fund transfer 这块我把单笔用户出入金 operation、批量资金搬运 transfer、过程 step 审计拆开。非 instant 的 deposit / withdrawal 会先进入 requested，再由任务按 token 分组 collect，后续通过 Gateway、Bridge、Alpaca、Broker、CashSettler 等步骤推进，所有步骤都有状态、txHash、失败原因和重试上下文。

三、2 分钟项目讲法

这个项目的背景是 RWA / 股票 token / fund token 交易系统里，很多业务状态来自链上事件，比如用户 deposit、withdraw、Gateway transfer、fund subscription / redemption、token transfer 等。如果只在 API 层维护状态，很容易和链上事实不一致。所以我负责做了一套 indexer，把链上事件变成后端可查询、可审计、可恢复的数据投影。

Indexer 的链路是：BlockWsService 订阅链上新区块，NewBlockListenerService 用 HTTP 轮询兜底并更新 latest block；NewBlockListener 根据每条链、每个 productType 的同步游标计算 block range，批量拉 eth_getLogs，把日志写入 indexer_event_log；然后 NewEventLogListener 事件驱动加定时扫描未解析日志，交给 EventResolverService。EventResolverService 在启动时扫描所有 EventHandler，按合约类型和 topic 分发，事务内更新业务表和 resolved cursor，事务外通过 hook 做 Redis、Slack、broker mapping、fund transfer 推进等副作用。

出入金这块更复杂，因为它不是一个 tx 就结束。用户单笔 deposit / withdrawal 会先由 Cashier 事件生成 indexer_cash_deposit_operation 或 indexer_cash_withdrawal_operation。instant 的直接 settled；非 instant 的会被 FundTransferTask 按 chain、product、token 分组 collect，发起链上 collect，并记录 indexer_fund_transfer_initiate_request 防止重复发起。Gateway 的 DepositCreated / WithdrawalCreated 事件出现后，会创建 indexer_fund_transfer 主状态，并把 operation 绑定到 transfer，写入 Collected step。

另外我也负责了 fund transfer 里的 buffer 水位重平衡。系统会定时读取 CashSettler / Cashier 的 credit buffer 和 withdrawal buffer 状态，按配置的 low / high / target 水位计算是否需要调拨。如果某一侧低水位，会从另一侧可用余量补到目标附近；如果某一侧高水位，会释放到另一侧。调拨不是直接改数据库，而是发起 BUFFER_WITHDRAWAL_TO_CREDIT 或 BUFFER_CREDIT_TO_WITHDRAWAL 类型的链上 initiate request，再复用后面的 Gateway / transfer / step 状态机推进。

后续资金流通过 RwaFundTransferProcessFactory 和多个 step handler 推进。比如入金可能走 Collected -> Bridge -> Processed -> Confirmed -> Consumed；出金可能走 Collected -> AlpacaOmJournal -> AlpacaSwap -> BrokerRequest -> Processed -> Bridge -> Confirmed -> Consumed。主表保留当前状态和关键金额、txHash；step 表保留每一步的来源、状态、action chain、txHash、retry 次数、typed extra。这样产品查询看主表，运维排查看 step，失败恢复也有上下文。

跨链这块我会区分“桥协议显示 filled”和“业务最终结算”。Bridge step 里会记录 bridgeId、source/destination chain、input/output token、quote、receive txHash、Across/CCTP 状态、receipt blockHash/finality 和输出金额。桥侧 ready 且 source / destination receipt 都过确认数后，状态机还要继续调用 Gateway confirm，把最终到账金额、rate target、platform cost 写到链上；最后 Consumed 阶段调用 CashSettler settle，等 DepositConsumed / WithdrawalConsumed 事件回来，transfer 才会标记 success。

四、系统边界和职责

Indexer 负责什么

  • 监听新区块和合约事件。
  • 根据 focus address 过滤关注合约。
  • 原始事件日志入库。
  • 按 contractType + topic0 分发 handler。
  • 把链上事件投影成业务 current-state / history / balance / transfer step。
  • 推动后处理 hook，例如账户 WS 更新、Slack 告警、fund transfer process signal。

Fund Transfer 负责什么

  • 识别非 instant deposit / withdrawal。
  • 将多笔 operation 聚合为一个 transfer。
  • 维护 transfer current-state。
  • 维护 transfer step 审计链路。
  • 处理 Gateway / Bridge / Alpaca / Broker / CashSettler 的链上链下协作流程。
  • 用锁、唯一键、client id、receipt 检查、step ordering 保障重入和恢复。

不要过度承诺的边界

  • 全局 indexer 层面有 blockSyncDelay 和 removed log 过滤，跨链 receipt 层面我补了确认数和 canonical blockHash 校验；如果面试官追问完整 reorg rollback，可以说“跨链到账确认是 reorg-aware 的，但全局业务投影 rollback 还可以继续体系化”。
  • 代码里有原始事件日志和游标，具备重放基础，但没有看到专门的 replay API。可以说“可以通过调整游标重放已入库事件，专门运维化 replay 工具需要再封装”。
  • 不要说“毫秒级”或“零丢失”。更稳的说法是“实时路径 + 兜底扫描 + 游标恢复，目标是降低丢事件和重复处理风险”。

五、核心链路

1. Indexer 链路

  1. BlockWsService 通过 WebSocket 订阅 eth_subscribe("newHeads")。
  2. NewBlockListenerService 每 5 秒 HTTP 查询 eth_blockNumber 作为兜底，和 WebSocket 一样进入 updateBlockNum。
  3. updateBlockNum 用 chain 维度 CAS 和 blockNum > latestBlock 判断过滤重复触发，再更新 indexer_event_sync_record.latest_block，发布 NewBlockEvent。
  4. NewBlockListener 按 chain + productType 用虚拟线程处理。
  5. 根据 syncedBlockNumber + 1、latestBlock - blockSyncDelay 和 maxBlocksPerRequest 计算 block range。
  6. BlockUtils 批量调用 RPC 获取 block 和 logs，失败按配置重试并切备用 RPC。
  7. IndexerEventLogService 保存原始日志，推进 syncedBlockNumber / latestEventId。
  8. NewEventLogListener 监听 NewEventLogEvent，同时每秒扫描未处理日志。
  9. EventResolverService 在事务内按 handler 路由解析，推进 resolvedEventId。
  10. handler 更新业务表，返回 hook 做事务外动作。

2. Deposit 链路

  1. 交易 API 构造 deposit calldata 或发送 tx。
  2. 用户 tx 先记录到 trading channel order tx，后续通过 txHash 回填 operationId。
  3. DepositRequestedHandler 监听 Cashier DepositRequested，创建 cash_deposit_operation=requested。
  4. 如果是 InstantDeposit，直接 settled + is_instant=true，更新 cash balance 和 history。
  5. 非 instant operation 被 FundTransferTask 扫描，条件是 requested、非 instant、没有 transferId。
  6. 按 chain / productType / token 分组，满足阈值或最大条数后调用 collectDeposits。
  7. 保存 indexer_fund_transfer_initiate_request=submitted，记录 operationIds、idsHash、txHash。
  8. DepositCreatedHandler 监听 Gateway DepositCreated，创建/更新 fund transfer，绑定 operationIds，operation 进入 processing。
  9. 写入 Collected step，完成 initiate request。
  10. 状态机继续推进 Bridge / Processed / Confirmed / Consumed。
  11. DepositSettledHandler 把 operation 置为 settled，写 balance history、cash balance、Redis 账户更新、Slack。
  12. DepositConsumedHandler 把 transfer 置为 success。

3. Withdrawal 链路

  1. 交易 API 构造 withdraw calldata 或发送 tx。
  2. WithdrawalRequestedHandler 监听 Cashier WithdrawalRequested，创建 cash_withdrawal_operation=requested，并扣减 cash balance。
  3. instant withdrawal 直接 settled + is_instant=true。
  4. 非 instant withdrawal 被 FundTransferTask 按 token 批量 collect。
  5. WithdrawalCreatedHandler 创建 fund transfer，绑定 withdrawal operations，写 Collected step。
  6. 默认链下路径先进入 AlpacaOmJournal，创建 OM -> CRD journal。
  7. AlpacaSwap 下 BUY IOC 单，把 credit 换成 token 数量。
  8. BrokerRequest 发起 Alpaca crypto withdrawal，并等待 broker txHash。
  9. Processed 阶段调用 Gateway stage/process withdrawal incoming，跨链时携带 bridge data。
  10. Bridge 等待/完成 Across 或 CCTP bridge，读取目标链 receipt / provider 状态，并做确认数与 canonical blockHash 校验。
  11. Confirmed 使用 bridge output amount 计算最终到账金额、rate target、platform cost，并调用 Gateway confirm。
  12. Consumed 调用 CashSettler settleWithdrawals 或 buffer finalize，等待 Gateway consumed event 把 transfer 置 success。
  13. WithdrawalSettledHandler 把 operation 置为 settled；如果 payout failed，则主状态仍是 settled，但写 failed_payout_amount。

六、关键设计

1. 原始事件日志和业务投影分层

设计上先写 indexer_event_log，再解析业务表。

这样做的价值：

  • 出问题时能看到原始 topic、data、txHash、block、logIndex。
  • resolvedEventId 可以和 latestEventId 对比，判断解析积压。
  • 可以基于已入库日志做局部重放。
  • handler 失败不会影响已经抓取到的原始事件。

面试表达：

我没有把抓日志和业务处理绑死，而是做了 raw event log 和业务投影分层。抓链只负责把可信事实落库，解析服务再按游标推进。这样即使某个业务 handler 因为依赖数据未准备好失败，也不会丢掉原始事件，后面可以继续扫描重试。

2. EventHandler 策略路由

EventResolverService 启动时扫描所有 EventHandler，构建：

ContractType -> Topic0 -> EventHandler

新增事件只需要实现：

  • contractType()
  • topic()
  • resolveEvent(BlockResolveEventDto dto)

价值：

  • 避免一个超大的 switch。
  • 不同业务事件独立维护。
  • 统一事务、游标、tx record、hook 逻辑仍然集中管理。

3. WebSocket 实时 + HTTP / Scheduled 兜底

实时路径：

  • BlockWsService 订阅 newHeads。
  • 收到新区块后调用 NewBlockListenerService.updateBlockNum。

兜底路径：

  • NewBlockListenerService 定时查询 blockNumber，也调用同一个 updateBlockNum。
  • NewEventLogListener 定时扫描未解析事件。

重复触发怎么处理：

  • updateBlockNum 对同一条链用 AtomicBoolean 做 CAS，WebSocket 和 HTTP 同时进来时只有一个会更新。
  • updateBlockNum 只有在 blockNum > latestBlock 时才更新和发布事件；同一个 block 或更旧 block 会直接返回。
  • NewBlockListener 下游按 chain + productType 再做一次 CAS，避免同一个产品线同时拉日志。
  • 真正拉日志不是按通知的单个 block 盲扫，而是按 DB 里的 syncedBlockNumber + 1 到 latestBlock - blockSyncDelay 计算区间。
  • saveAllEventLog 保存后推进 syncedBlockNumber / latestEventId，下一次触发会从新游标继续。
  • indexer_event_log 还有 (event_id, chain_id) 唯一索引，解析层用 resolvedEventId 控制只处理未解析事件。

稳妥边界：

  • 这里的设计允许“重复触发”，但通过游标和幂等控制避免“重复消费”。
  • 代码里 NewBlockEvent 被下游 CAS 忽略时不会排队；如果 latestBlock 已经更新，但没有后续更高 block 再触发，理论上可能延迟到下一次新区块或下一次能推进的触发。要进一步增强，可以给 block log 抓取层加一个 scheduled scanner，主动检查 syncedBlockNumber < latestBlock - blockSyncDelay。

面试表达：

WebSocket 和 HTTP 不是两套独立扫链逻辑，而是两个触发源，最终都进入同一个 updateBlockNum 和 syncedBlockNumber 游标链路。重复通知本身允许发生，但同链 CAS、blockNum > latestBlock、chain-product CAS、event log 唯一索引和 resolvedEventId 会把重复消费挡住。

4. chain + productType 维度的并发控制

实现里对不同链、不同 productType 可以并行，但同一个 chain-productType 用 AtomicBoolean 防止并发处理同一段游标。

价值：

  • 多链多业务线可以并行。
  • 同一游标不会被两个线程同时推进。
  • 虚拟线程适合 RPC / DB 这种 I/O 密集任务。

5. Cash Operation / Fund Transfer / Step 三层模型

三层模型：

  • cash_deposit_operation / cash_withdrawal_operation：用户单笔操作。
  • fund_transfer：一笔资金搬运动作的 current-state。
  • fund_transfer_step：链上、链下、外部 API、合约调用的过程审计。

为什么不只用一张表：

  • 用户查询关心单笔 operation 当前状态。
  • 资金系统关心 transfer 是否 pending/success/failed。
  • 运维排查关心卡在哪一步、哪个 tx、哪个外部系统、失败原因是什么。

面试表达：

如果把所有过程都塞进主表 JSON，短期能跑，但排查和重试会很痛苦。所以我把 current-state 和 step audit 拆开。主表服务查询，step 表服务审计和恢复。

6. initiate_request 防重复发起

FundTransferTask 发起 collect 后，不是只依赖链上事件回来，而是先记录一条 indexer_fund_transfer_initiate_request：

  • type：collect_deposit / collect_withdrawal / buffer...
  • status：submitted / completed / failed
  • operationIds
  • idsHash
  • txHash

价值：

  • 避免 tx 已发出但 Gateway 事件尚未回来时重复 collect。
  • txHash 唯一索引可以挡重复提交。
  • receipt 失败后可以标记 failed，保留错误原因。

7. FundTransferIdCodec 和 idsHash

FundTransferIdCodec 从 transferId 解码：

  • direction
  • srcChain
  • dstChain
  • tokenId
  • crossChain

再结合 idsHash 判断 purpose：

  • 用户 deposit / withdrawal
  • buffer withdrawal -> credit
  • buffer credit -> withdrawal
  • bootstrap credit buffer

面试表达：

transferId 本身不是随机字符串，它承载了方向、源链、目标链和 token 信息。purpose 不完全靠外部传参，而是结合 direction 和 idsHash 推导，这样事件解析时能从链上事实恢复 transfer 语义。

8. Buffer 水位重平衡

这块解决的问题是：出入金系统里同时存在 credit buffer 和 withdrawal buffer。某一侧过低会影响后续入金/出金处理能力，某一侧过高又代表资金结构不均衡。代码里通过 FundTransferTask.runBufferMonitor 做定时水位检查，并把重平衡动作接入原来的 fund transfer initiate request 和状态机。

核心策略：

  • 配置层按 settlement 开关 buffer.enabled，并配置 lowWatermarkPercent / highWatermarkPercent / targetWatermarkPercent 和 pollIntervalSeconds。
  • 读取链上状态时，DefaultFundTransferBufferStatusReader 从 CashSettler 获取 credit buffer / capacity，从 Cashier tokenConfig 获取 withdrawal buffer / capacity、decimals、depositRate、withdrawalRate。
  • 每次计算会把 capacity 乘以 low / high / target 百分比，得到两侧各自的低水位、高水位和目标水位。
  • 如果 credit 低于 low，并且 withdrawal 高于 low，就发起 BUFFER_WITHDRAWAL_TO_CREDIT，原因是 low_water_rebalance。
  • 如果 withdrawal 低于 low，并且 credit 高于 low，就发起 BUFFER_CREDIT_TO_WITHDRAWAL，原因也是 low_water_rebalance。
  • 如果 credit 高于 high，且 withdrawal 低于 target，就把 credit 释放到 withdrawal，原因是 high_water_release。
  • 如果 withdrawal 高于 high，且 credit 还有 capacity room，就把 withdrawal 转到 credit，原因是 high_water_release。

幂等和安全边界：

  • readonly indexer 不发起链上交易。
  • 同一 chain + productType 使用 fund-transfer:buffer:{chainId}:{productType} Redisson 锁。
  • 如果已经存在 pending 的 buffer transfer，或者已经有 submitted 的 buffer initiate request，就跳过。
  • 计算金额时同时考虑 token decimals、deposit / withdrawal rate、capacity room、minTransferAmount / minWithdrawalAmount。
  • 每轮 scope 只创建一个 rebalance action，避免一次扫描连续打出多笔调仓。
  • 保存 initiate request 时 operationIds 为空，idsHash 是空列表 hash；extra 里记录 rebalance reason、调仓前 credit / withdrawal buffer 和 token amount，后续事件回来能识别成 buffer purpose。

面试表达：

我做 buffer 水位重平衡时没有把它设计成一个单独的黑盒任务，而是接到 fund transfer 的 initiate_request 和状态机里。任务只负责判断低水位、高水位和目标水位，真正的资金动作仍然走链上 CashSettler，再由 Gateway event 创建 transfer 和 step。这样水位调拨也有 txHash、状态、失败原因和重试上下文，排查方式和普通出入金一致。

9. 跨链 Bridge 到账确认

跨链不是一个步骤就能说成功。我在设计里把它拆成四层：

  • bridge provider 层：Across / CCTP 是否已经在目标链完成 receive / fill。
  • finality 层：source / destination receipt 是否达到配置确认数，且 receipt.blockHash 仍然匹配 canonical block。
  • Gateway 层：Gateway 是否接受最终到账金额并发出 Confirmed event。
  • CashSettler 层：最终是否执行 settleDeposits / settleWithdrawals，并通过 Consumed event 把 transfer 标记 success。

入金和出金的跨链方向不同：

  • 跨链入金：Collected -> Bridge -> Processed -> Confirmed -> Consumed。先在源链 Gateway 发起 bridge，等 BridgedForDeposit 事件把 Bridge step 标为 success；之后 BridgeFundTransferStepHandler.finalizeBridgeIfReady 去确认桥侧是否真的完成，然后用 bridge output amount 进入 Processed。
  • 跨链出金：Processed -> Bridge -> Confirmed -> Consumed。ProcessedFundTransferStepHandler 会先构造 bridge data，调用 Gateway processWithdrawalIncoming，同时预写 pending Bridge step；BridgedForWithdrawal 事件回来后再进入 Bridge finalize，ready 后把 bridgeInOutputAmount 写成 amountReceived，再去 Gateway confirm。

Across 的确认逻辑：

  • 发起前调用 Across /suggested-fees 拿 quote，记录 outputAmount、quoteTimestamp、input/output token，并校验 slippage。
  • finalize 时用 /deposit/status?depositTxnRef={sourceTxHash} 查询状态。
  • 再读取源链 tx receipt 里的 FundsDeposited，拿 depositId / inputAmount / outputAmount。
  • 如果 Across 返回 filled，会读取目标链 fill tx receipt，并解析 FilledRelay 事件，用 originChainId + depositId 校验是不是同一笔 bridge。
  • 对源链 FundsDeposited 和目标链 FilledRelay 都做 finality gate：receipt 必须达到配置确认数，并且用 receipt.blockNumber 回查 canonical blockHash，防止短 reorg 下把临时 receipt 当到账。
  • FilledRelay 还会校验 log address 是配置中的 Across SpokePool，避免只靠 topic 匹配误认其它合约日志。
  • 只有目标链 receipt 成功、过确认数、blockHash canonical、SpokePool 地址匹配、FilledRelay 匹配且 outputAmount 合法时，Bridge step 才 ready。

CCTP 的确认逻辑：

  • 发起前 bridge data 里带 maxFee、minFinalityThreshold、destinationCaller。
  • finalize 时调用 Circle Iris /v2/messages/{sourceDomain}?transactionHash={sourceTxHash} 查询 message、attestation、eventNonce、status、delayReason。
  • attestation 未 ready 时，Bridge step 保持 pending，并记录 CCTP status / delayReason。
  • attestation ready 后，在目标链 MessageTransmitter 调用 receiveMessage(message, attestation)。
  • receiveMessage tx receipt 也会走同样的 finality gate：先确认 status success，再等确认数和 canonical blockHash。
  • 只有 receiveMessage tx 过 finality 后，才把 bridgeInReceiveDone 或 bridgeOutReceiveDone 标为 true；如果提示 nonce / attestation already used，会记录 receiveByOther=true，并继续用链上状态校验目标链已经被其他执行者完成。

幂等和恢复：

  • Bridge / Processed / Confirmed / Consumed 每个合约调用都会先检查已提交 txHash；receipt 未失败就不重复提交，receipt failed 才清理 txHash、记录 submitted_tx_failed、递增 retry。
  • BridgeStepExtra 保存 bridgeId、destChainId、input/output amount、input/output token、quoteTimestamp、provider type、receiveTxHash、provider status、delayReason。
  • BridgeStepExtra 也保存 source / destination receipt 的 blockNumber、blockHash 和 finality 状态；如果确认数不够或 blockHash 不匹配，就保持 Bridge pending，而不是推进到 Confirmed。
  • FundTransferTask.runExistingTransfers 会定时扫描 pending transfer，重新发布 process signal；卡在 provider pending、attestation pending、receipt pending 的 transfer 不会丢。
  • RwaFundTransferProcessFactory 对单个 transfer 加 Redisson 锁，避免同一笔 transfer 被多个线程同时推进。
  • 如果本地 step 顺序没跟上，但链上已经 consumed，FundTransferOnChainStateReader.isConsumed 会让本地直接补成 success，避免事件乱序导致永久卡住。

面试表达：

我不会把 bridge tx 发出去就当跨链成功。代码里跨链成功至少要过四道关：桥协议侧确认目标链 receive/fill，source 和 destination receipt 都过确认数并确认 canonical，Gateway confirm 接受最终到账金额，最后 CashSettler consumed 事件回来。Bridge step 里会记录 provider 状态、目标链 receive tx、output amount、blockHash、finality 状态和 delay reason；pending 或 reorg 风险未消除时保持等待，失败 tx 会清理后重试，所以这是一个可恢复的状态机，而不是一次性脚本。

10. 外部 API 的幂等 client id

Alpaca / Broker 相关外部动作使用确定性 client id：

  • fund-transfer-om-journal-{transferId}
  • fund-transfer-swap-{transferId}-{attempt}
  • fund-transfer-broker-withdrawal-{transferId}

价值：

  • 重试时先按 client id 查已有请求。
  • 避免重复创建 journal/order/withdrawal。
  • attempt 后缀支持失败后新下单。

11. Step typed extra

RwaFundTransferStep 绑定 extra 类型：

  • CollectedStepExtra
  • AlpacaOmJournalStepExtra
  • AlpacaSwapStepExtra
  • BrokerRequestStepExtra
  • BridgeStepExtra
  • ProcessedStepExtra
  • ConfirmedStepExtra

价值：

  • 不再靠裸 JSON key 记忆字段。
  • 每个步骤的上下文有边界。

  • 面向审计、等待原因、重试上下文更清楚。

12. 状态机推进与事件回写解耦

Gateway event handler 负责写主表和 step，并通过 hook 发布 FundTransferProcessSignalEventDto。

RwaFundTransferListener 异步监听 signal，交给 RwaFundTransferProcessFactory：

  • 单 transfer Redisson 锁。
  • 检查本地是否 pending。
  • 检查链上是否已经 consumed。
  • 找到支持当前 step 的 handler。
  • handler 处理后返回 nextStep，再继续发布 signal。

价值：

  • 事件解析和外部动作推进解耦。
  • 每一步可以独立等待外部系统。
  • 可以从 pending transfer 定时恢复推进。

七、可靠性与一致性设计

防漏事件

  • WebSocket newHeads 实时触发。
  • HTTP blockNumber 轮询兜底。
  • 原始事件先落库。
  • event log 解析有定时扫描。
  • 游标记录 latest block、synced block、latest event、resolved event。

防重复处理

  • event log、operation、fund transfer、initiate request 有唯一键或唯一索引。
  • handler 多处先查 existing 再 update/save。
  • collect group、buffer、transfer 都有 Redisson 锁。
  • 外部 API 使用确定性 client id。
  • 已提交 txHash 会检查 receipt，失败才清理并重试。

水位重平衡防抖

  • pollIntervalSeconds 限制同一 scope 的 buffer 状态读取频率。
  • low / high / target 必须同时配置，且 low < target < high <= 100，配置非法会直接抛错。
  • 触发前先查 pending buffer transfer 和 submitted buffer initiate request，避免上一笔还没落事件时重复发起。
  • 调拨金额会被 capacity room、对侧 low 水位余量、最小转账金额和 rate / decimals 共同约束。
  • 每次 monitor 命中一个 rebalance action 后就返回，降低连续重平衡造成的链上 tx 风险。

跨链 pending 与到账确认

  • Bridge step 不把“已提交 bridge tx”等同于“跨链到账”，还会等 provider status、目标链 receipt、receive/fill event 和 outputAmount。
  • Across 会校验源链 FundsDeposited 和目标链 FilledRelay，用 depositId 关联同一笔跨链。
  • Across 的 FundsDeposited / FilledRelay receipt 都要过确认数和 canonical blockHash 校验，且 FilledRelay 必须来自 Across SpokePool。
  • CCTP 会等 Iris attestation，再在目标链执行 receiveMessage，并检查 receive tx receipt。
  • CCTP 的 receive tx 同样要等确认数和 canonical blockHash，避免目标链短 reorg 下误判到账。
  • 跨链 output amount 会写入 BridgeStepExtra，后续 Confirmed step 用这个金额计算最终到账、rate target 和 platform cost。
  • 如果 provider / attestation / receive tx / finality 还没 ready，step 保持 pending，waitLogReason / delayReason / receiveTxHash / blockHash 保留排查上下文。
  • pending transfer 会被 FundTransferTask.runExistingTransfers 定期重新发布 signal，继续从最新 step 恢复推进。

乱序与依赖未就绪

  • 缺少前置 operation 或前置 step 时抛 IndexerDataNotReadyException。
  • 事务回滚，不推进 resolved cursor。
  • 后续 scheduled scanner 继续重试。
  • step ordering 会要求前一步 success；如果链上已 consumed，则本地补 success 并跳过。

金额精度

  • cash operation 保存 human-readable numeric(38,18)。
  • fund transfer 设计从 raw numeric(78,0) 演进到支持 human-readable 精度。
  • 代码在写 step extra 时 humanize，处理时 rawize。
  • token 金额按 token decimals，credit 按 18 decimals。

监控和排查

  • fund_transfer_step.status 可查 pending/failed。
  • waitLogReason / waitLogAt 记录卡点原因。
  • retriedTimes 记录重试次数。
  • txHash、txBlock、actionChainId 可定位链上动作。
  • Slack 通知覆盖 cash requested/settled、fund rebalance/bootstrap 等场景。

八、面试高频追问与回答

1. 你这个 indexer 和普通扫链脚本有什么区别？

普通扫链脚本通常是拉日志后直接处理，失败后很难知道处理到哪里。我这套是服务化 indexer：有 WebSocket 实时、HTTP 兜底、原始日志表、同步游标、事件解析游标、handler 策略路由、事务边界和后处理 hook。它不是一次性脚本，而是可长期运行、可恢复、可扩展的链上数据投影系统。

2. 为什么要先存原始 event log，再解析业务表？

因为链上事件是事实源，业务解析会依赖数据库状态和外部系统，可能失败。先落原始日志可以把“抓链成功”和“业务处理成功”拆开。失败后不会丢事件，后面可以按 resolved cursor 继续处理，也方便排查原始 topic/data/logIndex。

3. 如果 WebSocket 断了，或者 WebSocket / HTTP 同时触发怎么办？

WebSocket 只是低延迟入口。NewBlockListenerService 还会定时通过 HTTP RPC 查询最新 blockNumber，和 WebSocket 一样进入 updateBlockNum。同时触发时，同一条链有 AtomicBoolean CAS；即使没并发，blockNum <= latestBlock 也会被过滤。下游真正拉日志时按 syncedBlockNumber 游标算区间，不是每个通知都重扫同一个 block。

稳妥回答可以补一句：这里是“重复触发可接受，重复消费要挡住”。如果 NewBlockEvent 在下游忙的时候被忽略，通常下一次更高区块被 WebSocket 或 HTTP 发现时会继续触发；更强的版本可以给 block log 抓取层再加一个 scheduled scanner，主动检查 synced 是否落后 latest。

4. 如何保证同一个事件不会重复写业务表？

第一层是 DB 唯一键，比如 operation 用 (chain_id, product_type, operation_id)，transfer 用 (chain_id, product_type, transfer_id)。第二层是 handler 幂等，先查 existing，有就 update，没有才 insert。第三层是游标和锁，同一 chain-productType 不并发推进同一个解析游标。

5. 如果事件乱序，比如 Gateway transfer 事件先到，但 operation 还没入库怎么办？

这种情况代码里会抛 IndexerDataNotReadyException，事务回滚，resolved cursor 不推进。后续定时扫描会重新处理这批 event log。这样不会为了吞掉异常而把游标推进，避免数据缺失。

6. 为什么 cash operation 和 fund transfer 要拆开？

cash operation 是用户视角的一笔 deposit/withdrawal；fund transfer 是资金系统视角的一次批量搬运，可能包含多笔 operation，还会跨 Cashier、Gateway、Broker、Bridge、Alpaca、CashSettler。拆开后，用户查询和资金审计互不干扰。

7. 为什么还需要 fund_transfer_step？

transfer 主表只适合保存当前状态，比如 pending、success、关键金额和 txHash。但面试官真正排查问题时会问“卡在哪一步、等哪个外部系统、重试了几次、哪个 txHash 失败”。这些都应该放 step 表。step 表能承载 sourceType、sourceName、status、actionChainId、txHash、retry、extra。

8. 非 instant 入金怎么走？

用户 deposit 后先由 Cashier 事件生成 requested operation。FundTransferTask 扫描非 instant、无 transferId 的 requested deposit，按 token 分组，满足阈值就调用 collectDeposits，并保存 initiate request。Gateway 的 DepositCreated 事件回来后创建 transfer、绑定 operation、写 Collected step。后续跨链时先 Bridge，不跨链直接 Processed，然后 Confirmed、Consumed，最后 Cashier DepositSettled 把 operation 置 settled。

9. 非 instant 出金怎么走？

withdraw requested 后创建 withdrawal operation，并扣减用户 cash balance。collect 后创建 transfer。默认链下路径会先做 Alpaca OM -> CRD journal，再用 AlpacaSwap 买目标 token，再 BrokerRequest 发起 crypto withdrawal。拿到 broker tx / 金额后进入 Processed，必要时 Bridge，最后 Confirmed 和 Consumed，Cashier event 再把 operation 置 settled。

10. 如何避免一笔 operation 被重复 collect？

FundTransferTask 只扫描 requested、非 instant、没有 transferId 的 operation。扫描时还会查 active initiate request，把已经 submitted/completed 的 operationIds 过滤掉。发起 collect 时对 chain/product/token 分组加 Redisson 锁。DB 层还有 operation 唯一键和 initiate request txHash 唯一索引。

11. initiate_request 有什么用？

它记录 collect 或 buffer 调仓的发起动作。因为 tx 发出后，Gateway Created 事件可能还没回来，如果不记录中间态，定时任务可能重复发起 collect。initiate_request 保存 type、operationIds、idsHash、txHash、status，后续 Gateway event 回来再标 completed，receipt 失败则标 failed。

12. transfer purpose 是怎么判断的？

FundTransferIdCodec 先从 transferId 解 direction、srcChain、dstChain、tokenId。然后根据 idsHash 判断 purpose：普通 operationIds 的 hash 是 user deposit/withdrawal；zero idsHash 是 buffer 调仓；特殊 bootstrap idsHash 是 credit buffer bootstrap。

13. 外部 Alpaca / Broker API 怎么保证幂等？

不是每次重试都新建。Journal、order、crypto withdrawal 都有确定性 client id，例如 fund-transfer-om-journal-{transferId}、fund-transfer-swap-{transferId}-{attempt}、fund-transfer-broker-withdrawal-{transferId}。重试时先查 client id 对应记录，有 broker id 就同步状态；只有失败或无有效订单时才进入下一次 attempt。

14. Bridge 失败或 pending 怎么办？

Bridge step 会记录 bridgeId、source/destination chain、input/output token、quote、receive tx、provider 状态等 extra。处理时会先看是否已有提交 txHash，receipt 未失败就不重复提交；如果 provider finalize 未 ready，就保留 pending 和 wait reason，后续信号或定时任务继续推进。

15. 如果某个合约调用 tx 已经提交但失败了怎么办？

step handler 会通过 txHash 查 receipt。如果 receipt 是 failed，会清理 step 或 transfer 上的 submitted txHash，写 waitLogReason，比如 submitted_tx_failed，增加 retriedTimes，然后允许下一轮重新提交。

16. 为什么 step extra 要做 typed DTO？

之前如果把所有过程字段堆在一个 JSON 里，字段来源和含义很难维护。现在每个 step 绑定自己的 extra 类型，比如 BridgeStepExtra、BrokerRequestStepExtra、ConfirmedStepExtra。这样代码读写更清楚，也能减少 JSON key 写错和含义混乱。

17. 出金 payout failed 为什么主状态还是 settled？

代码设计里 WithdrawalPayoutFailed 表示 payout 失败上下文，但 withdrawal operation 主状态仍按 settled 处理，同时把失败金额写到 failed_payout_amount。这样可以表达“这笔 withdrawal 流程已完成结算处理，但 payout 结果有失败金额需要后续处理”，而不是把用户操作永远卡在 requested。

18. 如何处理跨链和非跨链的差异？

transfer 里有 srcChain、dstChain、isCrossChain。Collected 后，如果 deposit 是跨链，先走 Bridge，再 Processed；非跨链可以直接 Processed。withdrawal 也会根据 isCrossChain 决定是否构造 bridge data，以及 Processed 后是否进入 Bridge。

19. 这个系统如何支持恢复？

恢复点有几层：event log 可按 resolved cursor 重试；pending transfer 会被定时任务扫描并重新发布 process signal；step 中保存已提交 txHash 和 wait reason，能判断是等待外部系统、等待链上事件，还是 tx failed 后需要重试。

20. 链重组怎么说？

稳妥回答：

indexer 层面我通过 blockSyncDelay 和 removed log 过滤降低 reorg 风险；跨链到账确认上，我额外做了 receipt 确认数和 canonical blockHash 校验，所以不会把短 reorg 里的临时 FilledRelay 当成最终到账。但我不会把它夸成全局完整 rollback 引擎，如果后续要加强全业务投影，可以继续补 event log canonical 状态、业务投影版本和可逆 ledger。

21. buffer 水位重平衡解决什么问题？

它解决的是资金结构不均衡的问题。系统有 credit buffer 和 withdrawal buffer，两侧分别服务不同方向的资金处理。如果某一侧长期低水位，后续对应方向的出入金可能没有足够 buffer；如果某一侧长期高水位，资金利用也不均衡。所以 FundTransferTask 会定期读链上 buffer 状态，把两侧维持在 low / high 之间，并尽量往 target 靠。

22. low / high / target 三个水位分别怎么用？

low 是补水触发线，低于 low 才考虑从另一侧补；high 是释放触发线，高于 high 才考虑向另一侧释放；target 是计算调拨金额的目标线。比如 credit 低于 low，会尝试从 withdrawal 的 low 以上余量转一部分到 credit，金额最多补到 target，同时不能超过 credit capacity room 和链上最小转账金额约束。

23. 为什么要区分 low_water_rebalance 和 high_water_release？

这两个原因代表不同的业务意图。low_water_rebalance 是某一侧低水位，需要补充能力；high_water_release 是某一侧超过高水位，需要释放冗余。它们最终可能映射到同样的两个动作类型：BUFFER_WITHDRAWAL_TO_CREDIT 或 BUFFER_CREDIT_TO_WITHDRAWAL，但在 initiate request extra 和 step audit 里保留 reason，排查时能知道这笔调拨是补水还是释放。

24. 如何避免 buffer 重平衡重复发起？

有几层保护：第一，同一 chain + productType 有 Redisson buffer 锁；第二，发起前会查是否已有 pending 的 buffer transfer，包括 withdrawal->credit、credit->withdrawal 和 bootstrap credit buffer；第三，还会查是否已有 submitted 的 buffer initiate request；第四，tx 发出去后先保存 initiate_request，Gateway event 回来后再完成它。这样即使定时任务重复扫描，也不会因为事件还没回来就连续发起多笔。

25. buffer 调仓如何复用普通 fund transfer 状态机？

buffer 调仓不是直接更新余额，而是发起链上 CashSettler calldata：initiateWithdrawalToCredit 或 initiateCreditToWithdrawal。这会生成 BUFFER_WITHDRAWAL_TO_CREDIT 或 BUFFER_CREDIT_TO_WITHDRAWAL 类型的 initiate request，后续 Gateway Created 事件回来后创建 fund transfer。因为 operationIds 为空，idsHash 是空列表 hash，FundTransferIdCodec 可以把它识别成 buffer purpose，然后继续走 Collected、Processed、Confirmed、Consumed 这些 step。好处是审计、txHash、失败重试和运维排查都复用原来的框架。

26. 跨链怎么确认到账？

我会分四层回答。第一层是 bridge 层：Bridge step 不只看 bridge txHash，而是等 Across / CCTP provider 状态和目标链 receipt。Across 会查 deposit status，再解析源链 FundsDeposited 和目标链 FilledRelay；CCTP 会等 Iris attestation，并在目标链执行 receiveMessage。第二层是 finality 层：source / destination receipt 都要达到配置确认数，并用 receipt.blockNumber 回查 canonical blockHash，避免短 reorg 误判到账。第三层是 Gateway confirm：用 bridge output amount 作为最终到账金额，调用 confirmDeposit 或 confirmWithdrawal。第四层是 CashSettler consumed：只有 DepositConsumed / WithdrawalConsumed event 回来，transfer 才置为 success。

27. 为什么不能 bridge tx 成功就认为跨链成功？

bridge tx 成功只说明源链发起动作成功，不代表目标链资产已经到达或被 Gateway 接受。比如 Across 还要等 relayer fill，CCTP 还要等 Circle attestation 和目标链 receiveMessage。所以代码里 Bridge step 会继续 finalize，拿到目标链 receive tx / fill tx、provider status 和 output amount 后才进入下一步。

28. Across 和 CCTP 的确认方式有什么区别？

Across 更像 provider fill 模型：发起前拿 quote，记录 outputAmount 和 quoteTimestamp；到账确认时查 /deposit/status，再用源链 FundsDeposited 的 depositId 去匹配目标链 Across SpokePool 的 FilledRelay。CCTP 是 message + attestation 模型：先从 Iris 查 message 和 attestation，attestation ready 后在目标链 MessageTransmitter 调 receiveMessage。两者最后都会经过统一 finality gate：receipt success、确认数足够、blockHash 仍在 canonical chain。

29. 如何保证跨链过程不会因为 pending 卡死？

不是靠一次性同步等待，而是靠状态机恢复。Bridge step 会保存 provider type、status、delayReason、receiveTxHash、input/output amount、receipt blockNumber、blockHash、finality status 等上下文；如果 provider 没 ready、确认数不够，或者 canonical blockHash 校验不通过，就保持 pending。FundTransferTask.runExistingTransfers 会定时扫描 pending transfer，重新发布 process signal，从当前 latest step 继续推进。每个 step 还会检查已提交 txHash 的 receipt，pending 不重提，failed 才清理并重试。

30. 面试官问“你们如何保证跨链成功”，怎么稳妥回答？

不要说“绝对保证”，更稳的说法是：

跨链本身依赖 Across / CCTP 这类外部协议，我们不能承诺外部协议永远成功。但系统层面保证的是：每一步都有可观测状态、可恢复上下文和幂等重试。我们不会把 bridge tx 发出就当成功，而是等 provider 状态、目标链 receipt、Gateway confirm 和 CashSettler consumed event。失败或 pending 会停在对应 step，记录 wait reason 和 txHash，由定时任务继续恢复推进。

31. 如果以太坊或目标链发生 reorg，怎么避免误判到账？

我做了一个 finality gate，不是拿到 success receipt 就直接推进。对 Across 来说，源链 FundsDeposited 和目标链 FilledRelay 都要满足：receipt status success、receipt.blockNumber 距离当前链头达到配置确认数、用 receipt.blockNumber 回查出来的 canonical blockHash 和 receipt.blockHash 一致。对 CCTP 来说，目标链 receiveMessage receipt 也走同样校验。如果确认数不够，就保持 Bridge pending；如果 blockHash 不一致，说明可能被 reorg 影响，会记录 wait reason 并重新 finalize，而不是进入 Confirmed。

面试可以这么说：

我们把“provider 说 filled”和“链上 finality 足够”拆开。Across API 返回 filled 只是线索，真正进入 Confirmed 前，还要校验目标链 FilledRelay receipt 已过确认数且仍在 canonical chain。这样短 reorg 不会把临时日志当成最终到账。

案例 1：设计链上事件 indexer

S：背景

T：任务
设计一套能持续同步、多链多产品线、可恢复、可扩展的链上事件 indexer。

案例 2：设计出入金 fund transfer 状态机

S：背景
非 instant 出入金不是单次交易完成，涉及 Cashier、Gateway、Broker、Alpaca、Bridge、Settler 多个系统，且有等待、失败、重试和对账需求。

T：任务
设计一个既能面向用户查询，又能面向运维审计和故障恢复的资金流模型。

A：行动
我拆了三层表：operation 表表示用户单笔出入金；transfer 表表示一次资金搬运 current-state；step 表表示过程审计。非 instant operation 由定时任务批量 collect，initiate request 记录 tx 发起状态。Gateway event 创建 transfer 后，状态机通过 step handler 推进 Collected / Bridge / Processed / Confirmed / Consumed，外部 Alpaca/Broker 动作用 deterministic client id 保证幂等。

R：结果
用户侧可以查询单笔 operation 状态，资金侧可以查询 transfer 当前状态，运维侧可以通过 step 看到卡点、txHash、wait reason 和 retry 次数。系统具备重复事件、外部 API 重试、tx 失败重提、pending transfer 恢复的基础能力。

案例 3：设计 buffer 水位重平衡

S：背景 出入金系统里 credit buffer 和 withdrawal buffer 分别承担不同方向的资金能力。如果其中一侧长期低水位，后续资金处理会受影响；如果一侧过高，说明资金结构需要释放或调拨。

T：任务 设计一个自动水位监控和重平衡机制，并且要和已有 fund transfer 审计、幂等、重试能力保持一致。

A：行动 我在 FundTransferTask 里增加 buffer monitor 阶段，按 scope 读取链上 buffer 状态，用 low / high / target 三个水位计算调拨方向和金额。低水位时从另一侧可用余量补到目标附近，高水位时释放冗余；金额计算同时考虑 capacity、rate、token decimals 和链上最小金额。发起前加 buffer 维度 Redisson 锁，并检查 pending buffer transfer 和 submitted initiate request，避免重复发起。发起后保存 BUFFER_WITHDRAWAL_TO_CREDIT 或 BUFFER_CREDIT_TO_WITHDRAWAL initiate request，把 rebalance reason 和调拨前水位写进 extra。

R：结果 buffer 重平衡不再是脱离主链路的临时脚本，而是复用 fund transfer 的链上事件、transfer current-state、step audit、txHash 追踪和失败恢复机制。面试时可以强调这是资金调拨能力和可审计状态机的一次整合。

案例 4：设计跨链到账确认与恢复

S：背景 非 instant 出入金涉及跨链 bridge，单纯提交源链 bridge tx 不能证明目标链到账；Across / CCTP 还会有 provider pending、attestation pending、目标链 receive tx pending，以及 source / destination chain reorg 风险。

T：任务 设计跨链 transfer 的到账确认、失败恢复和最终结算链路，避免资金状态因为外部 bridge 延迟或事件乱序而卡死。

A：行动 我把跨链业务动作拆成 Bridge、Confirmed、Consumed，并在 Bridge 到 Confirmed 之间加 finality gate。Bridge step 里记录 bridgeId、source/destination chain、input/output token、quote、provider type、receiveTxHash、provider status、receipt blockNumber/blockHash 和 delayReason。Across 路径通过 suggested-fees quote 构造 bridge data，finalize 时查询 deposit status，并用源链 FundsDeposited 和目标链 SpokePool FilledRelay 校验同一笔 depositId；CCTP 路径则等 Iris attestation，ready 后在目标链执行 receiveMessage。两种路径都要等 receipt 达到配置确认数，并用 blockNumber 回查 canonical blockHash。Bridge ready 后才把 outputAmount 交给 Confirmed step，Confirmed 调 Gateway confirm，最后 Consumed 调 CashSettler settle，并等 Consumed event 把 transfer 标 success。

R：结果 跨链链路从“一笔 tx 发出”变成“可观测、可恢复、可审计、reorg-aware”的状态机。bridge pending、确认数不足或 blockHash 不匹配都会停在 Bridge step 并记录原因，tx failed 会清理并重试，pending transfer 会由定时任务重新发布 process signal，最终成功以 CashSettler consumed 事件或链上 consumed 状态为准。

先看结论：

  • 这个项目当前真实架构是 Router -> Settlement -> Vault。

2. 项目到底在做什么

这是一个 RFQ 协议执行层。

RFQ 的意思是：用户先拿到一份报价，再把这份报价带到链上成交。

这个项目把一笔成交拆成三层：

  1. 用户入口层：Router
  2. 协议结算层：Settlement
  3. 做市商执行层：Vault

可以把它想成一句话：

用户把钱交给 Router，Router 把单子交给 Settlement，Settlement 验完规则后再命令 Vault 真正完成兑换。

  • Settlement 不负责做市，它只负责协议规则和结算正确性。
  • Vault 不负责用户入口，它只负责执行 maker 侧报价。

7. Router 详解

源码：../src/Router.sol

7.1 Router 的定位

Router 是用户侧入口，不是最终裁判。

它主要负责：

  • 校验输入数组
  • 聚合多条 RFQ quote
  • 从用户或 relayer 收到 input token
  • 调 Settlement
  • 最后把多余资产退回

7.2 Router 支持哪些入金方式

有三类：

  1. 普通 ERC20 transferFrom
  2. Permit2 allowance 或 Permit2 signature
  3. 原生 ETH，内部包成 WETH

也就是说，Router 解决的是“用户的钱怎么安全进系统”，不是“这笔报价是否有效”。

7.3 为什么有 relayer 模式

因为调用者不一定是资产拥有者。

项目允许：

  • msg.sender == from：用户自己发交易
  • msg.sender != from：relayer 代发交易

但 relayer 模式不是随便转用户资产，必须走 Permit2 witness 签名，把下面这些参数全部绑住：

  • from
  • to
  • inputToken
  • outputToken
  • amountIn
  • amountOutMin
  • deadline

这样 relayer 不能拿到签名后偷偷改接收人或滑点。

7.4 Router 的关键设计点

  • 所有 quote 的 inputToken 必须一致
  • 所有 quote 的 outputToken 必须一致
  • Router 是逐条调用 Settlement，不是自己算 output
  • 聚合最小输出量 amountOutMin 是在全部 quote 执行后做总量检查
  • 如果是原生 ETH 输入，Router 会先包成 WETH，再按 ERC20 流程走

8. Settlement 详解

源码：../src/Settlement.sol

8.1 Settlement 的定位

Settlement 是整个协议的规则执行中心。

它做的事包括：

  • 校验 RFQQuote 平台签名
  • 校验 executor == address(this)
  • 校验 deadline
  • 校验 feeRate
  • 消耗 maker nonce
  • 计算时间衰减后的 amountOutMin
  • 控制 vault 回调拉款
  • ©最终检查 to 的余额增量

8.2 Settlement 不直接信 vault 的返回值

这是一个很关键的设计。

Settlement 在调用 vault 前会记录 to 的余额，在 vault 执行后再看余额变化。

所以它真正信的是：

“用户地址实际收到了多少 token/ETH”

而不是：

“vault 函数嘴上说它给了多少”

这能降低 vault 返回值造假的风险。

8.3 Partial fill 规则

当前协议允许 partial fill，但不是无限制。

规则是：

  • amountIn 不能大于 quote 的 amountIn
  • 向下偏离最大 60%
  • 等价于最少要成交原 quote 的 40%

所以：

  • 50% fill 可以
  • 40% fill 可以
  • 39% fill 会回滚

8.4 Time decay 规则

time decay 由 RFQLib.decayedAmountOut(...) 负责。

它的语义可以理解成：

  • 报价会随着时间衰减
  • 衰减窗口、起始时间、最大下调比例、指数都由 ConfidenceExtractedValue 决定
  • Settlement 会先算“衰减后的 full-fill output”
  • 再按当前实际 amountIn 等比例换算最小 output

公式不是特别复杂，思路是：

  1. 先得到一个衰减后的基准 decayedOut
  2. 再按 actualAmountIn / quotedAmountIn 比例缩放

9. Vault 详解

Settlement 只管规则，真正的 maker 执行逻辑在 vault。

9.1 MMVaultExample

源码：../src/MMVaultExample.sol

它的定位是“第三方 MM 参考实现”。

它做的事：

  • 只允许 mmQuote.executor 调用
  • 校验 mmQuote.vault == address(this)
  • 校验 deadline
  • 本地校验 maker 签名
  • 调 Settlement.rfqSettleCallback(amountIn) 拉 input
  • 从自身库存发 output

你可以把它理解成：

一个有库存的做市商金库，拿到 input 后，直接从自己库存给用户发货。

这类 vault 不需要池子，不需要路径，只需要库存。

9.2 V3BasedVault

源码：../src/V3BasedVault.sol

它的定位是“V3 池执行型 vault”。

它并不直接持有 output 库存，而是：

  1. 先从 Settlement 收到 input
  2. 解码 mmQuote.extraData
  3. 调用 CL 池的 swap
  4. 在池子回调时支付 input
  5. 拿到 output 后转给用户

这里 extraData 会编码：

  • clPool
  • zeroForOne
  • sqrtPriceLimitX96
  • routeData

9.3 V3 callback 为什么要做状态保护

因为 V3 池成交时会反向回调 vault，要求 vault 支付 input token。

所以 vault 必须知道：

  • 当前允许哪个 pool 回调
  • 当前允许支付哪个 input token
  • 当前最多能支付多少 input

当前实现用 transient 状态保存：

  • activePool
  • activeInputToken
  • activeInputBudget

这样可以防止：

  • 非预期池子乱回调
  • 回调扣错币种
  • 池子多扣 input

关系图如下：

flowchart TD
    S[Settlement] --> V[V3BasedVault]
    V -->|swap| P[V3 Pool]
    P -->|callback| V
    V -->|check activePool| G1{caller == activePool?}
    G1 -->|no| X1[revert]
    G1 -->|yes| G2{amount <= activeInputBudget?}
    G2 -->|no| X2[revert]
    G2 -->|yes| PAY[transfer input token to pool]

10. 签名、资金、权限 三条线分开看

理解这个项目最有效的方法，是把三个维度拆开。

10.1 签名线

  • RFQQuote.rfqSignature 由平台 signer 签
  • Settlement 验平台签名
  • MMQuote.mmSignature 由 maker 签
  • vault 本地验 maker 签名

10.2 资金线

  • 用户资产先到 Router
  • Router 再给 Settlement 授权
  • Settlement 不直接留钱，而是通过 callback 把 input 打给 vault
  • output 最终直接发给 to
  • 剩余 input 由 Router 退回

10.3 权限线

  • Router 是用户入口
  • Settlement 必须是 quote 指定的 executor
  • vault 只能被指定 executor 调用

11. Native Token 和 WETH 的处理方式

项目对原生 ETH 的思路是：

  • 协议内部尽量都当成 WETH 处理
  • 只有用户接口和最终转账时才做 unwrap

所以：

  • native input 会先包成 WETH
  • native output 本质上通常是先收到 WETH，再 withdraw
  • vault 的 receive() 对非 WETH 来的 ETH，会再包回 WETH

这套设计能让内部资金逻辑统一，不需要到处单独分支处理原生币。

12.1 Router 不是最终验签层

  • Router 负责收款和聚合
  • Settlement 验平台签名
  • vault 验 maker 签名

12.2 两层 min out 不是一回事

  • 用户总滑点保护：Router.swap(... amountOutMin ...)

当前两个 vault 在本地基本不负责严格执行这个参数。

真正决定是否满足最小成交量的是 Settlement 的后置余额检查。

12.4 V3BasedVault 当前会把未用 input 留在 vault

如果池子实际只吃掉了一部分 input，剩余 input 当前会留在 vault。

这在测试里是明确锁定的当前语义，不是偶然行为。

案例一：Delulu Kafka 消费链路 Channel 阻塞导致 goroutine 泄露

一句话定位

Delulu 的 EVM Transfer 消费服务在处理 Kafka 消息时，会按 Holder 拆分任务并发提交到固定 Worker；提交协程通过 ProcessedChan 同步等待处理结果，但这个等待没有超时和取消机制。一旦 Worker 被慢查询卡住或异常退出，等待结果的 goroutine 就永久阻塞，进一步卡住 WaitGroup 和 Kafka offset 提交，最终形成“goroutine 持续增长、内存上涨、Kafka Lag 扩大”的级联故障。

30 秒回答

Delulu 出现 Kafka Lag、goroutine 和内存持续上涨，但 CPU 不高。pprof 定位 Worker 因数据库无超时或任务 panic 不再返回，Handler 无法提交 offset。修复时把带 Deadline 的 Context 传给 Worker，设置全局并发上限并做任务级隔离。最终 goroutine 稳定，Lag 回落。

2～3 分钟完整回答

Delulu 的 Market 服务消费 Kafka EVM Transfer 事件并更新 Holder 余额。线上一次告警表现为 Kafka Lag、Pod 内存和 goroutine 持续上涨，但 Broker、分区和 Rebalance 正常，进程没有 Crash，CPU 也未打满。重启只能短暂恢复，所以我判断不是单纯消费能力不足，而是任务没有释放。

我先排除 Kafka 和网络问题，再抓取 goroutine profile，发现大量堆栈停在 submitHolderWork 等待 ProcessedChan，上层又卡在 WaitGroup.Wait()，导致 Handler 无法返回和提交 offset。数据库虽有慢请求，却不足以单独解释 goroutine 持续增长。

反查 Worker 生命周期后发现，数据库调用使用无 Deadline 的 Context，慢查询会长期占住 Worker；任务 panic 时 recover 放在循环外，整个 Worker 会退出。提交协程又没有超时或取消协议，只能无限等待结果。于是新消息不断转成内存中的等待协程，Channel 是阻塞点，真正根因是任务生命周期无上界且缺少背压。

修复时，我为每个任务创建带 Deadline 的子 Context 并传入 Worker，数据库和 RPC 都使用它；提交队列和等待结果同时监听 Context 与服务退出信号。再用全局 Semaphore 限制真实在途任务，令牌只在任务结束或确认取消后释放；recover 下沉到任务边界，保证单任务异常不会杀死 Worker。最后注入数据库超时、Worker panic、队列打满和服务取消进行验证。修复后 goroutine 保持稳定上界，下游恢复后 Lag 能自行回落，慢依赖只会降低消费速度，不再演变成进程级泄露。

现象为什么容易误判

  • Kafka Lag 上涨，很容易先怀疑 Broker 性能、分区数不足或 Rebalance。
  • Pod 没有 Crash，CPU 也不一定很高，因为泄露的 goroutine 大部分处于阻塞状态，不消耗 CPU。
  • 扩大 Channel 或增加 Worker 后，问题会短暂缓解，但只是在增加缓冲区，根因仍然存在。
  • 重启可以立即恢复，使问题看起来像偶发网络故障，但运行一段时间后仍会再次出现。

核心数据流

Kafka EVM Transfer Message
        ↓
按 chain + token + holder 分组
        ↓
每个 Holder 启动 goroutine
        ↓
Hash 到固定 Worker Queue
        ↓
Worker 查询数据库并更新 Holder
        ↓
ProcessedChan 回传结果
        ↓
WaitGroup 结束，Kafka Handler 返回并提交 Offset

故障发生时，链路停在：

Worker 未返回结果
        ↓
<-work.ProcessedChan 永久等待
        ↓
WaitGroup.Wait 永久等待
        ↓
Kafka Handler 不返回、Offset 不提交
        ↓
在途 goroutine 和 Kafka Lag 持续增长

排查过程

1. 从业务和 Kafka 指标确定故障边界

重点检查：

  • Kafka records-lag-max、各 partition lag 和消息生产速率；
  • Consumer Group 是否频繁 Rebalance；
  • 单条 Kafka 消息处理时长；
  • Holder 更新吞吐量；
  • Pod CPU、RSS、GC 和 goroutine 数量。

关键判断是：如果 Kafka Lag、goroutine 和内存同时增长，但 CPU 没有同步打满，优先怀疑 goroutine 阻塞，而不是计算量不足。

2. 排除 Kafka Broker 和 Rebalance

  • Broker 没有 Under Replicated Partition；
  • Consumer Group 成员稳定，没有持续加入和退出；
  • 网络吞吐和拉取消息耗时正常；
  • 相同消息在重启后能够继续处理。

由此确认 Kafka 是被下游 Handler 卡住，而不是 Kafka 自身停止分发。

3. 使用 pprof 查看 goroutine 阻塞点

curl http://127.0.0.1:6060/debug/pprof/goroutine?debug=2
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine

大量重复堆栈集中在：

EvmTransferConsumer.Consume
  -> submitHolderWork
     -> <-work.ProcessedChan

这说明 goroutine 已经完成任务投递，但一直收不到 Worker 的完成信号。

4. 反向追踪为什么没人发送结果

主要有两个触发路径：

  • Worker 在无 Deadline 的数据库或 RPC 调用中长期阻塞，执行不到 ProcessedChan <- err；
  • 单个任务 panic 后，外层 recover 虽然捕获异常，但 Worker 循环整体退出，分配给这个 Worker 的队列失去消费者。

最终根因不是“Channel 本身不可靠”，而是发送方可能永久消失，接收方却没有超时、取消或关闭协议。

修复方案

第一层：让等待可取消、可超时

taskCtx, cancel := context.WithTimeout(ctx, processTimeout)
defer cancel()
work.Ctx = taskCtx // Context 随任务传给 Worker，DB/RPC 必须使用它

select {
case err := <-work.ProcessedChan:
    return err
case <-taskCtx.Done():
    return taskCtx.Err()
}

任务投递 Worker Queue 时也监听 taskCtx.Done()，避免队列已满后发送方继续堆积。结果 Channel 容量固定为 1；Worker 发送结果时同时监听任务 Context，接收方已超时后也不会被迟到结果反向阻塞。

第二层：限制最大在途任务

使用 Semaphore 或有界 Worker Pool，把并发上限从“消息里有多少 Holder 就启动多少 goroutine”改成固定配置值。Semaphore 令牌在任务真实结束或 Worker 确认取消后才释放，不能在提交方刚超时、Worker 仍执行时提前释放，否则实际并发仍可能越过上限。下游变慢时让压力停留在 Kafka，而不是转化成进程内不可见的 goroutine 和内存。

第三层：隔离单任务异常

把 recover 放到每次任务执行的边界：

  • 单个任务 panic 时回传错误；
  • ProcessedChan 容量为 1，回传时也监听任务 Context；
  • Worker 继续消费后续任务；
  • 每个进入队列的任务最终都必须得到成功、失败、超时或取消中的一种结果。

第四层：下游调用必须有 Deadline

  • 带 Deadline 的子 Context 随任务结构传入 Worker；
  • 数据库查询、更新以及 RPC、Redis 调用全部使用该任务 Context；
  • 服务退出时取消 Context，使所有排队和等待中的任务能够快速退出。

第五层：失败交给可靠机制处理

  • 可重试错误让 Kafka 重新消费；
  • 超过阈值进入重试 Topic 或死信队列；
  • 使用事件 ID 或 blockNumber + txIndex + logIndex 作为唯一键，先写事件处理记录，再在同一数据库事务内更新 Holder 余额；
  • 只有该事务提交后才把消息视为成功，唯一键冲突表示事件已经处理；
  • 不在内存中无限等待一个不确定结果。

验证方式

  • 注入数据库慢查询，确认等待任务按时超时，goroutine 数量不持续增长；
  • 在 Worker 内主动触发 panic，确认当前任务返回失败而 Worker 继续处理下一条；
  • 将 Worker Queue 压满，确认最大 goroutine 数不超过配置上限；
  • 重启或取消服务 Context，确认排队和等待中的协程可以退出；
  • 恢复下游后观察 Kafka Lag 是否能够自动回落；
  • 连续对比多次 goroutine profile，确认不再出现相同阻塞栈持续累积。

结果与亮点

这次问题让我确认，goroutine 便宜不代表可以没有生命周期管理。Channel 也不能只设计正常的发送和接收路径，还必须定义发送方消失、接收方退出、队列满、服务关闭时如何收口。最终我们把 Kafka 消费链路从无界并发改成有界背压，使下游异常只会降低消费速度，不再演变成进程级资源泄露。

可强调的亮点：

  • 从 Kafka Lag 一直追到 Go runtime 的 Channel 阻塞栈；
  • 能区分触发条件、阻塞点和真正根因；
  • 没有用扩大 Channel、增加 Worker 或定时重启掩盖问题；
  • 同时解决并发上界、任务超时、Worker 存活和 Kafka 失败重试；
  • 把 goroutine 生命周期和 Kafka offset 提交语义联系起来。

常见追问

为什么有 Worker Pool 还会 goroutine 泄露？

Worker 数量虽然固定，但提交任务的 goroutine 并不固定。每个 Holder 都会启动一个提交协程，而它们会无限等待 Worker 的处理结果。Worker Pool 只能限制真正执行任务的数量，不能自动限制等待队列和等待结果的 goroutine。

ProcessedChan 是带缓冲的，为什么仍然会阻塞？

Buffer 只解决发送方和接收方速度暂时不一致的问题。如果 Worker 永远没有执行到发送语句，Buffer 里没有任何数据，接收方仍然会永久等待。修复后结果 Channel 容量为 1，且发送和接收两端都监听任务 Context，分别覆盖“无人发送”和“迟到结果无人接收”。

为什么不直接把 Channel 再扩大？

Channel 变大只能容纳更多积压，无法处理 Worker 卡死、发送方消失和无超时等待。积压从 Kafka 转移到进程内后反而更难观测，而且会增加内存风险。

为什么让压力留在 Kafka 更合理？

Kafka 本身就是可持久化、可监控、可重放的缓冲层。进程内 goroutine 和 Channel 是易失状态，服务重启后全部丢失。下游过载时应该通过有界消费形成背压，而不是把 Kafka 消息无限转换成内存任务。

如何保证超时后不会重复更新余额？

超时只表示本次调用结果不确定，Kafka 可能会重试。消费时以 chainId + txHash + logIndex 等事件唯一键先写处理记录，并在同一个数据库事务内更新 Holder 余额；唯一键冲突时跳过余额更新。这样处理记录和余额要么一起提交，要么一起回滚，不能只依赖普通 Upsert 或“消息只消费一次”。

案例二：腾讯视频会员券系统重构与渐进式迁移

一句话定位

在不能停机、不能改变既有调用方接口语义的前提下，把发券、领券、查券和规则逻辑高度耦合的旧单体，渐进式拆分为可独立扩容的券服务；同时迁移过亿历史数据、持续追平线上增量，通过事实源控制、影子比对和按用户灰度保证用户券链路粘性，并让新旧入口始终共用跨用户桶的权威活动库存。

30 秒回答

腾讯视频会员券旧单体耦合发券、领券、查券和硬编码规则，数据过亿且不能停机替换。我们用兼容层和绞杀者模式迁移，历史数据跑约半个月，以 CDC 追增量，影子比对后按 userId bucket 灰度用户券链路；新旧入口始终共用权威活动库存。通过原子预占、数据库同步事务和唯一键收紧并发风险，热点查询由接近 1 秒降到约 10～15ms，各服务可独立扩容。

2～3 分钟完整回答

这个项目的难点不是简单拆微服务，而是在过亿存量券数据和持续线上流量下，兼容旧调用方并做到可验证、可灰度、可回滚。旧单体耦合发券、领券、查券和硬编码规则，热点活动查询接近 1 秒，并发边界也不清晰，又不能停机一次性替换。

我们先盘点接口语义、错误码、数据模型、规则、调用方和 SLA，补齐链路追踪、延迟、数据差异与库存监控。然后用兼容层保持旧接口不变，按低风险读链路、实时领券、批量发券的顺序逐步替换。

用户券数据按 userId 分片。过亿历史数据用幂等脚本迁移约半个月，CDC 持续追平增量，再做总量、分桶、抽样和关键字段校验。迁移初期旧库是事实源，新系统先做影子读和双读比对；读链路稳定后按 userId bucket 灰度。切主前设置路由版本和旧侧写入围栏，让 CDC 追到确定水位并排空旧侧在途写，再原子切到新侧。需要回滚时，给新侧设置新路由版本和写入围栏，排空新侧 Handler 在途写，记录最终新→旧同步水位，等旧侧追到该水位后原子切回，再停止反向同步并按需恢复旧→新 CDC，不能在新侧仍可写时直接回滚。

userId bucket 只负责用户券数据和请求粘性；活动库存是跨桶全局状态，新旧入口共用权威库存。领券时，用户维度锁负责互斥，数据库唯一键兜底；活动维度原子预占库存，随后在数据库事务内同步写券实例和发券流水，提交后才返回成功，失败就补偿库存。

上线前做兼容测试、影子比对、数据校验、容量压测和故障注入，并用错误率、延迟、同步水位和库存偏差控制灰度。最终热点查询降到约 10～15ms，各服务可独立扩容；唯一约束、权威库存、补偿对账和容量隔离共同收紧了重复领取与超发风险，收益不是来自单一缓存技巧。

背景与约束

  • 旧单体同时承担发券、领券、查券和规则判断，模块之间共享数据结构和执行流程，任何修改都可能影响完整券链路。
  • 活动资格、券有效期和领取限制等规则大量硬编码，变更依赖发版，难以审计规则版本，也难以快速回退。
  • 单库单表存放过亿券数据，热点活动查询在高并发下接近 1 秒，实时链路与批量任务相互争抢数据库资源。
  • 并发控制缺少清晰边界，线上偶发同一用户重复领券、活动库存超发，以及批量发券失败后的漏发。
  • 外部调用方多，历史数据和线上增量持续变化，系统不能停机，也不能用“大爆炸”方式一次性替换。

最核心的五个难点

1. 接口语义和错误码兼容

兼容不只是 URL 和字段名相同，还包括默认值、空值、排序、分页、幂等语义、错误码以及超时行为。新旧系统对边界输入的处理一旦不同，调用方即使没有改代码也可能出现业务回归。因此迁移前必须形成接口契约，并通过录制流量回放和兼容性测试锁定行为。

2. 亿级历史数据迁移时持续承接增量

全量迁移运行期间线上仍在发券、领券和核销。如果只搬一次历史快照，迁移结束时新库已经落后；如果没有稳定的位点和校验方式，也无法证明增量是否完整追平。因此需要“全量快照迁移 + binlog/CDC 增量追平 + 多层数据校验”的组合。

3. 新旧系统一致性与事实源控制

迁移阶段必须明确哪个系统的结果对用户生效、哪个库是事实源。影子读和双读可以用于比较，但不能让两套结果同时影响用户；写链路也不能默认向两边随意双写，否则局部失败、重试乱序和版本覆盖会制造更难修复的不一致。

4. 按用户灰度并且可回滚

领券和查券必须对同一用户保持路由粘性。如果同一用户的一次写走新系统、下一次读走旧系统，即使 CDC 最终能追平，用户仍会短暂看到错券或重复领取。因此用户券数据与用户请求的灰度、回滚单元是 userId hash bucket，而不是随机请求。但活动库存是所有用户桶共同竞争的全局状态，不能随用户桶各自维护：新旧领券入口必须共用同一个权威库存服务和 Redis 库存命名空间；无法共用库存入口的活动只能整体切换。

5. 服务拆分后的跨服务一致性与容量隔离

服务拆分后，规则判断、用户领取资格和 Redis 活动库存不再与数据库券记录处于一个本地事务中。需要分别定义用户互斥、库存原子预占、数据库同步事务、失败补偿和对账机制；同时隔离实时查券、实时领券与批量发券的资源，避免某个依赖抖动或批量流量拖垮整条链路。

渐进式迁移过程

第一阶段：盘点现状并建立可比较基线

在改造前先完成五类盘点：

  • API：请求和响应字段、默认值、错误码、超时、幂等以及分页和排序语义；
  • 数据模型：券、活动、库存、用户领取记录之间的主外键和状态流转；
  • 规则：领取资格、次数限制、生效和过期条件，以及规则优先级；
  • 调用方：同步调用、批量任务、运营后台及其发布节奏；
  • SLA：旧链路的延迟分位、错误率、容量峰值、数据库负载和数据差异基线。

同时统一 traceId 和业务键，把入口、规则判断、库存扣减、券写入、Kafka 消费和数据库访问串到同一条 trace，并补齐延迟、错误率、重试、CDC 延迟、缓存命中率和库存差异监控。没有这些基线，就无法判断迁移是否真的更好，也无法为灰度设置停止条件。

第二阶段：用绞杀者模式拆服务

入口先增加兼容层，对调用方保持旧接口和错误码不变，内部再逐步把请求路由到新服务。新服务采用 tRPC，部署在腾讯 K8s 平台，按职责拆分：

  • 规则服务：管理规则配置、版本和计算；
  • 查券服务：承接用户券列表和可用券查询；
  • 领券服务：处理用户资格、幂等、库存与券实例创建；
  • 发券服务：处理运营批量发券和异步任务。

迁移顺序先读后写：先迁移低风险的查券链路，通过影子读积累 diff；再迁移实时领券；最后迁移批量发券。这样每一步的故障面更小，也能复用上一阶段验证过的数据和监控能力。

第三阶段：重构数据访问与迁移过亿历史数据

券数据按 userId hash 分表，让“查询某个用户的券”这一核心路径能够直接定位分片，并通过读写分离承担高并发查询。为保证读己之写，领券成功后的即时查询走主库，或让该用户在短时间内粘到主库；只有允许复制延迟的列表和历史查询走从库。对于运营筛选、按活动聚合等不能由 userId 定位的查询，把可检索字段同步到 ES，避免跨分表扫描；ES 是查询索引，不是库存或券状态的事实源。

历史数据迁移采用可断点续跑、幂等写入的脚本，整体约半个月：

  1. 记录全量迁移起点的 binlog 位点，分批扫描旧库并写入新分表；
  2. 通过主键或稳定游标推进，避免大 offset 扫描和长事务；
  3. 全量迁移期间持续采集 MySQL binlog，通过 CDC 把新增和变更写入新库；
  4. 全量完成后继续消费增量，直到 CDC 延迟进入灰度门槛；
  5. 校验通过后才允许对应用户桶进入新链路。

校验分为四层：全局总量校验、按 userId hash bucket 的数量与聚合校验、随机及重点用户抽样、券状态/有效期/活动/版本等关键字段比对。脚本记录批次、游标、成功数和失败原因，失败任务可重跑而不会重复制造数据。

第四阶段：明确事实源，做影子验证和用户级灰度

迁移初期旧库是事实源，旧系统继续返回用户结果；CDC 单向同步到新库。新查券服务接收复制的影子请求或执行双读，将新旧结果标准化后做 diff，但差异只进入监控和排查队列，不影响线上响应。

灰度先从白名单开始，再按照 userId hash bucket 扩大。所有入口复用同一套路由规则，保证同一用户的查券、领券和后续查询始终落在同一套用户券链路。这个 bucket 只切用户券数据和用户请求；活动库存始终是跨桶全局状态，灰度期新旧领券入口共用同一个权威库存服务和 Redis 库存命名空间。若某个活动因旧协议或部署边界无法共用库存入口，就以活动为单位整体切换，不能让不同用户桶竞争两份库存。

用户桶切主采用可执行的四步协议：

  1. 为目标桶生成新的路由版本并设置写入围栏，旧版本请求不能越过围栏写入；
  2. 让旧→新 CDC 追到记录的确定水位，同时排空旧侧已经进入 Handler 的在途写；
  3. 原子切换该桶的主写路由，并停止该桶旧→新复制，确保任一时刻只有一个业务主写；
  4. 回滚窗口内，以来源标记、记录版本和业务幂等键将新侧变更同步到旧侧。

回滚必须对称执行：先给新侧设置新路由版本和写入围栏，阻止旧版本继续写入；再排空新侧 Handler 在途写，记录最终新→旧同步水位；等待旧侧追到该水位后原子切回旧路由；切回完成后再停止新→旧反向同步，并按需恢复旧→新 CDC。不能在新侧仍可写时直接切回。

切换后持续观察接口错误率、P99 延迟、新旧数据 diff、库存偏差、CDC 延迟和下游容量。回滚窗口结束后，旧系统进入只读观察期，只用于对账和应急查询，不再承诺快速切回；稳定后再逐桶扩大，直至全量。

第五阶段：规则服务与热点只读缓存

规则从代码中抽离并持久化到数据库，每次发布生成不可变规则版本，券或活动引用明确版本，便于审计和回滚。缓存层级统一定义为进程内 L1、Redis L2、数据库事实源，采用 cache-aside：数据库事务提交后删除 Redis L2，进程内 L1 按规则版本失效；任一层 miss 都向下一层回源，最终从数据库重建。

针对热门活动的只读配置，内部 hotkey proxy 识别热点，流计算聚合访问热度；Kafka 只传递规则版本或失效通知，不承担缓存存储。进程内 L1 和 Redis L2 都带版本与过期时间，旧版本通知不能覆盖新版本；消息丢失时仍可通过 TTL 和回源修复。两级缓存只保存可重建的规则或展示配置，不保存活动库存；库存必须留在权威库存服务的原子竞争边界内。

第六阶段：分别治理重复领券和库存超发

这两个问题看起来都发生在“领券”，实际属于不同竞争维度：

  • 用户维度：以用户和活动为粒度使用 Redis 分布式锁，避免同一用户的并发请求同时通过资格判断；即使锁过期或进程暂停，数据库中的 (userId, activityId/couponTemplateId) 业务唯一键仍做最终兜底。
  • 活动维度：所有用户跨 bucket 竞争同一份权威活动库存，新旧入口都调用同一库存服务并使用同一个 Redis 库存命名空间；通过 Redis INCRBY 原子预占，越界立即回补并返回库存不足。

库存预占成功后，在同一个数据库事务内同步写入券实例和发券流水，并由业务唯一键防止重复创建；事务提交后才向用户返回领券成功。数据库事务失败或超时确认失败时补偿 Redis 库存，补偿失败进入重试表，并由定时任务核对 Redis 库存、数据库库存流水和实际发券数。异步链路只承载通知、搜索索引等非关键派生数据。这是“同步落券 + 库存补偿和对账”的可恢复方案，不承诺跨 Redis 与数据库的 Exactly Once。

第七阶段：用 Kafka 承接亿级批量发券

批量任务先拆成可重试的小批次写入 Kafka，由 consumer 数量控制数据库写入并发。每个用户任务使用稳定键 (batchTaskId, userId, couponTemplateId)；consumer 在同一数据库事务内写券记录和任务处理状态，事务成功后才提交 Kafka offset。消息重投时由稳定键唯一约束识别已完成任务并跳过，因此适配 Kafka at-least-once 交付，但不宣称 Exactly Once。失败写入重试表，超过阈值进入人工处理队列，避免一个超大事务长期占锁或回滚。

批量发券使用独立 consumer group、线程池、数据库连接池和限流配置；依赖异常时熔断或暂停批量消费，让积压保留在 Kafka。这样批量任务变慢只会增加可观测的消息积压，不会抢光查券和领券的实时资源。

迁移验证与回滚

兼容性测试

  • 用旧调用方流量样本回放新兼容层，比对字段、默认值、排序、分页、错误码和超时语义；
  • 对空数据、过期券、重复请求、库存不足和规则切版等边界条件做契约测试；
  • 保证调用方不需要配合一次性升级。

影子流量和数据校验

  • 新旧查券结果标准化后做 diff，差异只告警，不影响用户响应；
  • 持续校验全局总量、用户分桶聚合、抽样记录和关键字段；
  • 监控全量迁移进度、binlog/CDC 位点和同步延迟，未追平的桶不得切流。

容量与故障验证

  • 对热点查券、并发领券和批量发券分别压测，验证服务、缓存、数据库和 Kafka 的容量上限；
  • 注入 Redis 超时、数据库主从延迟、Kafka 积压、CDC 中断和部分服务不可用；
  • 验证限流、熔断、重试、对账和容量隔离是否生效，确认批量链路不会拖垮实时链路。

灰度门槛与回滚机制

  • 将错误率、延迟、影子 diff、库存偏差、CDC 延迟和资源水位定义为灰度门槛；
  • 用户券路由均受配置开关、路由版本和写入围栏控制，切主操作可审计；
  • 切主前让旧→新 CDC 追到确定水位并排空旧侧在途写，原子切主后停止该桶旧→新复制；
  • 回滚窗口内按来源标记、记录版本和业务幂等键做新→旧同步；回滚时先给新侧设置新路由版本和写入围栏，再排空新侧 Handler 在途写并记录最终新→旧同步水位，等待旧侧追到该水位后原子切回旧路由，切回后才停止反向同步并按需恢复旧→新 CDC；
  • userId bucket 不切分活动库存；新旧领券入口共用权威库存，无法共用的活动只能整体切换；
  • 回滚窗口结束后旧系统只读保留，用于对账和应急查询，不再承诺快速回滚。

结果与亮点

重构完成后，高并发热点查询由接近 1 秒降到约 10～15ms，规则、查券、领券和发券服务可以根据各自压力独立扩容；业务唯一约束、权威库存原子预占以及对账补偿共同收紧了重复领券和库存超发风险。这个结果是数据分片与读写分离、缓存体系、规则解耦、清晰的一致性边界、Kafka 削峰以及依赖隔离的综合收益，不能归因于某一个缓存技巧，也不能简单归因于“拆成了微服务”。

可强调的亮点：

  • 在过亿存量数据和持续线上增量下，完成约半个月的可校验迁移；
  • 用兼容层和绞杀者模式控制调用方改造成本，按读、实时写、批量写逐步降低风险；
  • 用旧库事实源、影子 diff、单主写和用户分桶灰度避免迁移期的数据歧义；
  • 把用户重复领取和活动库存竞争拆成两个一致性边界分别治理；
  • 将规则版本化、只读热点缓存、库存原子扣减和批量削峰放在各自正确的位置；
  • 让每个灰度单元都有明确门槛、路由开关、同步位点和回滚路径。

常见追问

为什么不用一次性重构？

旧系统调用方多、数据过亿，而且发券和领券不能停。一次性替换会同时放大接口兼容、数据迁移、容量和回滚风险；一旦上线后出现问题，也很难判断是代码、数据还是流量模型导致。绞杀者模式可以先用兼容层稳定外部契约，再按读链路、实时写链路、批量链路逐步切换，让每一步都能验证和回滚。

如何保证迁移不丢数据？

在全量迁移开始时记录 binlog 位点，历史数据通过幂等脚本分批写入新库，迁移期间的新增和更新由 CDC 持续同步。全量结束后先等增量追平，再做总量、用户分桶、抽样和关键字段校验。只有 CDC 延迟和数据差异都进入门槛的用户桶才允许切流，失败批次保留游标并可重跑。

为什么按 userId 分片？

核心在线访问模式是“查询某个用户的券”和“某个用户领取券”，userId 能让绝大多数用户券请求直接定位单一分片，也天然适合作为请求灰度粘性键。按活动分片会让单个热点活动集中到一个分片，并且用户查券需要跨活动聚合。非 userId 的运营查询交给 ES 索引，不反向扫描全部分表。活动库存不随 userId 分片，而是所有桶共用权威库存服务；无法共用时按活动整体切换。

为什么不直接双写新旧库？

无约束双写无法天然一致：一边成功一边失败、重试顺序不同或旧值晚到，都可能让两侧状态分叉。我们保留一个明确的业务主写和事实源，再用 CDC 或受控同步复制变更；双读只用于比对，不影响结果。切写时以用户桶为单位改变主写归属，而不是让同一请求并行决定两边状态。

怎么回滚？

切到新侧前，用路由版本和旧侧写入围栏阻止旧版本写入，让旧→新 CDC 追到确定水位并排空旧侧在途写，再原子切主。需要回滚时，先给新侧设置新路由版本和写入围栏，排空新侧 Handler 在途写，记录最终新→旧同步水位；等待旧侧追到该水位后原子切回旧路由，切回后再停止反向同步，并按需恢复旧→新 CDC，不能在新侧仍可写时直接切回。窗口结束后旧系统只读观察，不再承诺快速回滚。活动库存始终由共享权威库存承接；不能共享时按活动整体切换。

Redis 锁和库存原子扣减分别解决什么？

Redis 分布式锁解决的是同一用户并发请求的互斥，防止两次请求同时通过领取资格判断；即使锁过期，数据库 (userId, activityId/couponTemplateId) 唯一键仍会拒绝重复落券。INCRBY 解决的是所有用户对同一权威活动库存的并发竞争。预占成功后，券实例与发券流水在同一数据库事务中同步写入，提交后才返回成功；事务失败就补偿库存。两者维度不同，不能互相替代。

规则缓存如何失效？

数据库是规则事实源，Redis 是 L2，服务进程内缓存是 L1。cache-aside 更新流程是数据库事务提交后删除 Redis L2，再通过 Kafka 发布版本或失效通知，让 L1 按版本失效；缓存 miss 时逐级回源并最终从数据库重建。旧版本通知不能覆盖新版本，TTL 负责兜住通知丢失，必要时可把活动重新指向上一规则版本。Kafka 只负责通知，不是缓存层。

Redis 与数据库之间如何保证一致？

先在共享 Redis 库存中用 INCRBY 原子预占，越界立即回补；再在同一个数据库事务内同步写券实例和发券流水，事务提交后才返回成功，失败则补偿 Redis。补偿失败进入重试表，定时任务按活动核对 Redis 库存、数据库库存流水和实际发券数。异步只用于通知和非关键派生数据，不把券记录异步落库，也不宣称跨 Redis 与数据库实现 Exactly Once。

批量发券如何避免拖垮实时链路？

批量任务通过 Kafka 削峰，以 consumer 数控制写入并发，并采用小批次短事务；每个用户任务以 (batchTaskId, userId, couponTemplateId) 为稳定键，券记录与处理状态在同一数据库事务内提交，成功后才提交 offset，重投由唯一约束跳过。批量发券和实时链路使用独立线程池、连接池、限流与熔断，下游异常时暂停消费，让压力留在 Kafka。这是 at-least-once 加业务幂等，不是 Exactly Once。

两个案例的统一收口

两个案例分别体现了“局部异步链路治理”和“大型系统渐进演进”。Delulu 的核心是为异步任务建立有上界的生命周期：任务必须可超时、可取消、可失败收口，并通过并发上限和 Kafka 形成背压。腾讯券系统的核心是先定义兼容边界、各类状态的事实源、灰度单元和回滚能力：userId hash bucket 只负责用户券数据与请求粘性，活动库存则由跨桶共享的权威入口承接。无论是修复线上故障还是重构大型系统，我都会先明确状态边界、数据所有权、失败语义和恢复路径，再决定并发、缓存、重试和拆分方案。

面试表达边界

  • Delulu 案例中，准确说法是“Worker 未返回导致接收 ProcessedChan 的 goroutine 永久阻塞”，不要只说“Channel 满了”。
  • Kafka Lag 是 goroutine 泄露的结果之一，仍需说明为什么 Handler 无法返回和 offset 无法提交。
  • 腾讯券系统案例中，不把“拆成微服务”当成全部收益；性能和稳定性提升来自分片、读写分离、缓存、并发控制、异步削峰和容量隔离的综合作用。
  • 不说双写天然一致。迁移期的准确说法是“明确单一业务主写和事实源，通过 CDC 或受控同步复制变更，双读只用于校验”。
  • 不把 userId bucket 说成所有状态的灰度单元；它只路由用户券数据和用户请求，活动库存必须由新旧入口共享，不能共享时按活动整体切换。
  • 不把 Redis 分布式锁和库存原子扣减混为一谈：前者解决同一用户请求互斥，后者解决活动维度的并发库存竞争。
  • 不把券实例写库说成异步最终一致；券实例和发券流水必须在数据库事务内同步提交，异步只处理通知和非关键派生数据。
  • 缓存命名统一为进程内 L1、Redis L2、数据库事实源；Kafka 只发送版本或失效通知。两级缓存都不能用于库存。
  • 不说实现了跨 Redis、数据库和 Kafka 的 Exactly Once；更准确的是“通过幂等、重试、补偿和定时校对实现可观测的最终一致性”。
  • Kafka 批量发券准确表达为“at-least-once 投递 + 稳定业务键幂等”，事务提交后才提交 offset。
  • 不虚构 QPS、用户数、分表数量或灰度百分比。可使用的事实是“过亿数据”“迁移约半个月”和“查询从接近 1 秒降至约 10～15ms”。
  • 如果需要进一步量化 Delulu 案例，只补充能够由真实监控证明的 goroutine 峰值、Kafka Lag 和恢复时间。
